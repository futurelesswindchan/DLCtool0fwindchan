## 2026-07-30: 主游戏识别改取第一个 addappid，不再要求带密钥

**背景**：原判据为「第一个带 key 的 `addappid` 调用即主游戏」。该判据在 Hubcap
格式下成立——其主游戏行写作 `addappid(2399830, 1, "b1ea599f...")`。

但 GitHub 快照源（SSMGAlt/ManifestHub2）的主游戏行不带密钥：

```lua
addappid(2399830)                                    ← 主游戏，无密钥
addappid(2399831, 0, "320e0bcc...")                  ← 主 Depot
setManifestid(2399831, "4735635872933062882")
```

原判据会跳过 2399830 而把 Depot 2399831 认作主游戏。后果有两重：`MainAppID`
错误导致部署文件名与历史记录全部记错游戏；且 2399831 被消耗为主游戏后不再进入
`Depots` 列表，其密钥与 manifest 一并丢失。

**结论**：

- **改取第一个 `addappid` 调用作为主游戏，带 key 时一并记入 `MainKey`。**
  依据是「主游戏必须最先注册」这一脚本语义要求——生成脚本时本工具自身遵循它，
  OST 侧同样依赖此顺序，两种源格式均满足
- **不采用「主游戏无 key」作为判据**。快照源恰好如此，但这是其生成流程的巧合而非
  语义保证。以巧合为判据，等于把另一个源的格式细节固化进解析器
- 主游戏无密钥时部署器已有处理（输出单行 `addappid` 并记警告），行为与源文件
  原样一致，不额外补密钥

**留待验证**：MAU 路径的 `fallbackMainKey` 在主 AppID 无密钥时会挑一个 depot 密钥
顶替，其注释称「生成脚本要求主游戏那行必须带密钥，否则已装本体的游戏会崩」。
若该说法成立，则快照源路径也需同等处理；若不成立，则 MAU 那处属过度防御。

倾向后者——快照源那 6.2 万分支的主游戏行都不带密钥，若真会崩，社区早已发现。
但此判断**无实测依据**，`deployer_ost.go` 中「Steam 会在校验阶段直接崩溃」这句
亦未经验证。保持现状（不补密钥，只记警告）是保守选择：照搬源文件原样不引入
新风险，而补一个不属于主 AppID 的密钥，其后果同样未知。

## 2026-07-30: 收录检测采用三态，仅 404 可排除候选源

**背景**：`probe` 原返回布尔值，`narrowToHits` 据此排除「未收录」的源。而 HEAD
请求失败的原因不止「资源不存在」一种——超时、连接重置、5xx、429 都会落入
同一个 `false`。

大陆直连 codeload 的失败率相当高。实测 `git ls-remote https://github.com/alex47exe/LuaMan`
一次耗 21 秒后报连接失败、一次报 `RPC failed; curl 56 Recv failure`，而同一时刻
`raw.githubusercontent.com` 经 curl 可正常访问。原 `lookupTimeout` 仅 8 秒，远短于
实测的失败耗时。

`narrowToHits` 原有一层兜底：全部探测失败时返回全部候选。但**部分失败的情形没有
兜底**——若 A 源探测成功而 B 源恰好抖动超时，B 会被彻底排除，即便它实际收录、
且下载阶段的四级镜像链本可取回。表现为「明明有清单却提示需要本地导入」。

**结论**：

- **`probe` 返回三态** `probeHit` / `probeMiss` / `probeUnknown`。只有服务端明确
  回应 404 才算 `probeMiss`；超时、连接重置、5xx、429、403 一律为 `probeUnknown`
- **`narrowToHits` 只排除 `probeMiss`**，`probeUnknown` 的源保留候选资格，交由
  下载阶段的镜像链兜底。检测是优化手段，不该拥有否决下载的权力
- 认证型源的错误**全部视为 `probeUnknown`**。凭据失效、额度耗尽都与「该游戏有无
  清单」无关，判为未收录会误导用户去找别的源
- **`lookupTimeout` 由 8 秒放宽至 15 秒**。过短的超时会把「网络慢」大量转化为
  `probeUnknown`，虽有候选资格保留兜底，但每个未探明的源都要在下载阶段白走一遍
  四级镜像链，反而更慢
- 判定逻辑抽出为纯函数 `narrowByProbeResults`，不涉及网络，由测试覆盖五种组合。
  该逻辑的失效方式是静默的——被误排除的源不报错，只是永远不被尝试

## 2026-07-30: 收录检测加并发上限，源数量增长不再线性放大请求

**背景**：`probeAll` 原为全源无限制并发。源数量为 3 时尚可，增至 7 个后会同时
向 codeload 发出 6 个请求（第 7 个是认证型源，走自己的域名）。

同一 IP 的突发请求可能触发限流，而限流响应（429/403）在新的三态判定下算作
`probeUnknown`——该源随即要在下载阶段白走一遍四级镜像链。即是说，**并发过高
反而使总耗时变长**。

**结论**：

- **以带缓冲 channel 作信号量，并发上限取 4**。七个源分两批完成，最坏情形为
  两倍单次超时，仍在可接受的等待范围内
- 该上限与 `enrichPackageDLCs` 的 `maxConcurrent = 4` 一致。两处都是对同一批公益
  代理与 GitHub 端点的并发访问，取同值便于将来统一调整
- **不按源类型区分并发额度**。认证型源虽走独立域名、不与 codeload 争抢配额，
  但为此引入分组限流的复杂度换不来可感知的收益

## 2026-07-30: 内置源列表在升级时按名称合并，只增不改

**背景**：`defaultRepoSources()` 仅在配置中的源列表为空时回填（`normalize` 的
既有逻辑）。这意味着新版本增加的内置源对老用户完全不可见——其 `config.json`
已存有旧版的 4 个源，非空，故不触发回填。

而 v2.0 目前暂时不提供自定义源的界面入口，用户也无从手动添加。表现为「升级后新源没
生效」，且界面上看不出任何原因。

**结论**：

- 新增 `mergeNewBuiltinSources`，按 `Name` 匹配，把配置中缺失的内置源补入列表
- **只增不改，已存在的条目原样保留**。不覆盖 `Enabled` 与 `Token`：前者是用户
  明确表达的意愿（手动停用过某个源），后者是用户自行申请的凭据。二者若因版本
  升级被重置，表现为「设置莫名恢复默认」，而用户很难把这现象与升级联系起来
- **新源追加在末尾而非按内置顺序插入**。这一取舍偏向「升级不改变现有行为」——
  新源作为额外兜底加入，不顶替用户已经在用的路径。代价是老用户的源顺序与新装
  用户不同，但顺序仅影响尝试次序，不影响可用性
- 合并返回新切片，不就地修改传入的列表。`normalize` 在持有锁的路径上被调用，
  就地修改会让调用方难以判断自己的切片是否已被改动

**测试锁定四条**：补入缺失源、不覆盖 Token 与 Enabled、已是最新时不产生重复、
不修改传入切片。其中第二条是最需要防回归的——它的失效直接导致用户丢凭据。

## 2026-07-30: 该站时间戳按美东时区解析，内嵌 tzdata 处理夏令时

**背景**：Hubcap 的 `/user/stats` 返回的 `api_key_expires_at` 形如
`2026-08-03T15:50:50.528769`，**不带时区标识**。原实现 `parseMSiteTime` 三个
layout 全部走 `time.ParseInLocation(..., time.UTC)`，函数注释亦写明「按 UTC 处理」。

但该站 lua 注释头写的是 `EDT`，据凭据生成时刻反推亦与美东时间吻合。按 UTC 解析
会使算出的到期时刻偏早数小时。

**结论**：

- **改按 `America/New_York` 解析**，而非写死 UTC-4 或 UTC-5。美东行夏令时，
  夏季为 EDT(UTC-4)、冬季为 EST(UTC-5)，任一固定偏移都会在换季后产生 1 小时误差
- **必须 `import _ "time/tzdata"` 内嵌 IANA 时区库**（约 450KB）。Windows 无系统
  zoneinfo，不内嵌则 `LoadLocation` 失败。且该失败是静默的——代码会退回 UTC，
  与修复前行为相同，问题看似消失实则未解
- `LoadLocation` 失败时退回 UTC 而非 panic。到期时刻偏早数小时只是提醒略微提前，
  不值得让整个额度面板不可用
- 测试同时锁定 7 月取 UTC-4 与 1 月取 UTC-5，以此验证内嵌确实生效——只测一个
  季节的话，退回 UTC 的情形在冬季测试中不会暴露

**原「偏早约 5 小时」的记载不准确**。草稿依 UTC-5 推算，但 7 月属夏令时应为
UTC-4，偏差是 4 小时。此细节不影响修复方式，但记录在此以免后续复核时困惑。

## 2026-07-30: 启用 Frameless，Aero Snap 经源码确认可白嫖系统实现

**背景**：`Frameless` 自 07-28 定案后一直推迟启用，卡在一个未验证的疑问上——
拖至屏幕边缘的 Aero Snap 在 Wails v2.11 下是否保留。若不保留，自绘标题栏
等于用一个视觉统一换掉一个高频的窗口管理习惯，这笔交易不划算。

**查证结果**（读 v2.11 源码，非推测）：

`internal/frontend/desktop/windows/frontend.go` 的 `startDrag()` 实现为：

```go
w32.ReleaseCapture()
w32.PostMessage(hwnd, w32.WM_NCLBUTTONDOWN, w32.HTCAPTION, 0)
```

即把后续过程**整个交还给系统的标题栏拖动循环**。Aero Snap、多显示器吸附、
拖离最大化态还原，全部由该循环负责，因此一并保留，无需自行实现。

`window.go` 的 `WM_NCCALCSIZE` 返回 0 只是让客户区吃掉整个窗口以隐去标题栏，
`WS_THICKFRAME` 样式仍在，故边缘缩放热区照常由系统提供——它位于客户区之外，
前端元素挡不住它。

**结论**：

- **启用 `Frameless: true`**（`main.go` 与 `wails.json` 同步）。Aero Snap 与边缘缩放
  为系统行为，零成本继承
- **不设 `DisableFramelessWindowDecorations`**。保留默认的 DWM 客户区扩展换来
  系统级窗口阴影、圆角与边框；关掉它就得自绘，而自绘阴影永远与系统主题对不齐
- **Snap Layouts（Win11 悬停最大化按钮的分屏浮层）确认不可用**。它要求
  `WM_NCHITTEST` 对该区域返回 `HTMAXBUTTON`，而自绘按钮位于 WebView 客户区内，
  命中测试到不了那里。属原生标题栏特权，无绕行方案，接受
- **双击最大化在 TopBar 自行绑定**，并排除按钮与链接——用户双击控件时的意图
  是连点该控件，不是改窗口形态
- **最大化状态以 `resize` 事件驱动同步**，而非点击时翻转本地布尔值。Aero Snap
  与 `Win+↑` 同样会改变窗口状态且不产生点击事件，只翻本地值必然错位。
  `resize` 覆盖全部途径且静止时零开销，代价是需 120ms 防抖——`WindowIsMaximised`
  是跨边界异步调用，缩放期间不防抖会打出上百次 IPC

**no-drag 的防漏措施**：按钮点击被识别为拖拽起始是 frameless 最高频的翻车点。
故 CSS 不逐个类名列举，改用 `.topbar button, .topbar a, .topbar input, .topbar select`
的宽泛选择器兜住——日后新增控件默认即被覆盖，不依赖施工者记得补一条规则。

## 2026-07-30: 打开本地目录改用 explorer，BrowserOpenURL 在 v2.11 起不可用

**背景**：`OpenDataDir` 点击后毫无反应，控制台仅一行
`ERR | Invalid URL shell metacharacters not allowed`。

根因不在本项目。Wails v2.11 给 `BrowserOpenURL` 加入了
`internal/frontend/utils/urlValidator.go`，其中两道关卡**各自独立地**否决了
Windows 本地路径：

```go
if scheme == "javascript" || scheme == "data" || scheme == "file" ||
   scheme == "ftp" || scheme == "" {
    return "", errors.New("scheme not allowed")   // ← 裸路径无 scheme，命中
}
shellDangerous := `[;\|` + "`" + `$\\<>*{}\[\]()~! \t\n\r]`  // ← 含反斜杠
```

即便绕过其一，另一条仍会拒绝。`app.go` 中「Wails 的 BrowserOpenURL 对本地
路径同样有效」这句注释写于 v2.9 时期，在 v2.11 下已不成立。

**结论**：

- **改用 `exec.Command("explorer", path)` 并只 `Start()` 不 `Wait()`**。
  explorer 在成功打开窗口的情况下同样返回退出码 1，据退出码判断成败会
  100% 误报失败
- **路径作为独立参数传入，绝不拼进命令字符串**。`exec.Command` 的变参形式
  不经 shell 解析，天然免疫注入。用户的 Steam 路径与主目录都可能含空格，
  而字符串拼接在含引号或 `&` 的路径下会变成命令注入面
- **`OpenURL` 保持使用 `BrowserOpenURL`**。它只放行 http(s)，URL 中不含反斜杠，
  两道关卡都不触发，实机验证可用。为「统一」而把它也改成 explorer 反而会
  失去 Wails 侧的校验
- 抽出 `openInExplorer` 供诊断包复用。非 Windows 平台直接返回失败——本项目
  仅面向 Windows，写一个跑不到的 `xdg-open` 分支只是虚假的可移植性

**同类风险的排查结论**：全项目仅 `OpenDataDir` 与 `OpenURL` 两处调用
`BrowserOpenURL`，后者不受影响。

## 2026-07-30: 诊断包采白名单式脱敏，凭据只报存在性不报片段

**背景**：封测将在 QQ 群进行，群聊中最常见的一句话是「把日志发上来我看看」。
而数据目录里的 `config.json` 明文存着用户自行申请的 M 站 API 凭据。

只要有一个人截图或直接发送该文件，其额度即归群友所有，而该站的封禁规则
相当硬。这不是理论风险——报障链路本身就在诱导用户去翻数据目录。

**结论**：

- **新增 `ExportDiagnostics`，定位是「替代危险行为的安全出口」而非便利功能**。
  它必须比手动翻目录更省事，用户才会选它。故导出后自动打开所在文件夹——
  用户拿到「已导出」提示却找不到文件，是这类功能最常见的失败方式
- **脱敏采白名单式投影**：独立声明 `maskedConfig` / `maskedRepoSource`，
  只含已知安全字段，而非拷贝 `AppConfig` 再置空 `Token`。差别在日后新增
  字段时显现——黑名单方式下，新增的敏感字段会**默认泄露**，且没有任何
  编译期或运行期信号提醒开发者补规则
- **凭据只描述存在性**（未填写 / 已填写 N 位 / 长度可疑），**连
  `maskSecret` 的前 8 位也不给**。日志里出现前 8 位可以接受——那用于比对
  「是否同一个密钥」；但诊断包流传范围更广，且此处没有任何需要比对密钥
  的场景，给出前 8 位纯属净增风险
- **取内存中的配置而非读磁盘 `config.json`**。磁盘文件可能含用户手工添加的
  未知字段，原样读入再序列化等于把未知内容一并带出。经 Go 结构走一遭，
  相当于用类型定义做了一次强制过滤
- **不含 `history.json` 与 `packages/`**。前者是用户装过哪些游戏，后者是清单
  内容本体，都与「工具为何出错」无关。且清单文件流入群聊会使性质从工具
  测试变成内容分发，这与本项目的职责边界直接冲突
- **日志只取最近 3 个**。日志按天轮转，报障通常发生在当天或前一天，而把半年
  日志全打进 zip 只会让群里传不动文件
- 单个日志读取失败只跳过不报错：诊断包宁可少一个日志也不该整体失败，
  而日志正被写入时的读取冲突在 Windows 上并不罕见

**测试锁定的关键一条**是「状态描述中不得出现凭据原值的任何可识别片段」。
它防的是日后有人为了「方便排障」在此拼上密钥前几位——那种改动看起来无害，
且不会有任何其他信号提示它把凭据推向了半公开场合。

## 2026-07-30: 构建身份注入程序内部，dirty 标记与哈希同等重要

**背景**：封测包将在群内分发。原计划仅把 git 短哈希打进发布文件名，理由是
「文件名与编译时的代码强相关，便于快速定位问题」。

该判断成立，但文件名**会丢**：用户下载后重命名、解压后只留 exe、转发给他人
时改名，哈希随即消失。而报障的典型时序是「用了三天后出问题」，那时压缩包
早已删除。

同时，封测期同一版本号会被反复重新构建（修一个 bug 打一次包，但 tag 未动），
此时版本号无法区分用户手里是哪一次构建——而这恰是报障时最需要确定的信息，
因为同样的现象在修复前后的两个包上表现完全相同。

**结论**：

- **哈希打在文件名与程序内部两处**。文件名便于分发时肉眼识别与口头指代，
  注入程序内部则跟随 exe 本身，诊断包与「关于」页永远带得出来
- **额外注入 `appDirty`，其重要性高于哈希本身**。带 dirty 标记的包所对应的
  代码**在仓库里根本不存在**，据其哈希 `checkout` 会得到另一份代码。若不
  显式标出，排障时会照着错误的代码找原因，而且完全察觉不到。封测期赶时间
  «改一行就编译发出去» 极易发生，这个标记是防自欺的
- **`dirty` 仅在注入值为字符串 `"true"` 时成立**，测试专门锁定此点。写成
  「非空即真」会把每个正常包都标成已修改（脚本在工作树干净时注入的是
  `"false"`），进而使警告彻底失去意义——用户看惯了就不再当回事
- **`Label` 由后端单点组装**，前端直接展示。这串文字会被用户抄进报障消息，
  也会写入诊断包，两处格式必须完全一致；各自拼接迟早不一致
- **未注入时不拼出 `dev (unknown)`**。既无信息又占位置，且会让人误以为
  `unknown` 是某个真实的提交
- **封测包版本号用 `2.0.0-rc.1` 而非 `2.0.0`**。否则封测包流传出去后，
  有人拿着 rc 版报障而维护者以为是正式版
- **发布文件名格式 `kazeusa-<版本>-<哈希>.exe`**，版本号在前。群聊中人们
  按版本号口头指代（「rc.1 那个包」），版本在前才便于排序与指称
- `release.ps1` **只构建，不上传、不打 tag、不动 git 状态**。发布脚本一旦
  越界去改仓库状态，出错时的回滚成本会陡增

## 2026-07-30: 搜索改按钮驱动，理由是网络现实而非交互偏好

**背景**：搜索原为输入即搜（`useDebounceFn` 400ms）。

Steam 商店接口在国内经常以 `wsarecv: An existing connection was forcibly
closed` 中断。实测输入 `monster` 期间，日志出现了 **5 次**「搜索失败」。

问题不在于浪费请求，而在于**归因**：用户看到连续 5 条报错，最合理的结论是
「这工具坏了」，而实际情况只是自己还没打完字。防抖无法解决这一点——它只能
减少次数，不能让失败与用户的意图对应起来。

**结论**：

- **改为按钮与回车显式触发**，移除防抖。请求次数交回用户掌控，一次点击对应
  一次结果，失败也就归因清晰
- **补「清空」按钮**。自动搜索取消后，清空输入不再自动收起结果列表，若无显式
  出口，用户想回到初始状态只能刷新页面
- **加载态由按钮文案承担**，移除原先绝对定位在输入框右侧的省略号指示器。
  按钮就在用户刚点击的位置，比右侧的省略号更容易被注意到
- 原记录中「`SearchView` 存在 AppID 直查的第二条入口，改造时两条触发时机
  要一致」的担忧**不成立**：纯数字判断在后端 `SearchGames` 内部完成，
  前端只有一个入口

**未采用「失败自动重试一次」**。重试会把一次失败变成两次等待，而在当前的
显式触发模型下，用户再点一次搜索的成本比自动重试更低且完全可控。该项留待
封测反馈决定。

## 2026-07-30: 彻底卸载后复位当前页，不跳转库列表

**背景**：`uninstall()` 成功后 `router.push({ name: 'library' })`。

**结论**：

- **改为把本页复位为状态 A（未入库）**。卸载常常是「装错了源、想换一个」的

## 2026-07-30: 「收录」与「有用」在界面上分离，先落文案后落对比表

**背景**：实测同一个 Monster Hunter: World（582010），7 个源全部报「确认收录」，
实得质量从 200 DLC 到 0 DLC：

| 源 | 结果 |
| :--- | :--- |
| Hubcap | 200 DLC / 8 Depot |
| MAU | 64 DLC / 2 Depot |
| MAU fork · tymolu233 | 63 DLC / 2 Depot |
| MAU 镜像 / bingyu50 | 解析失败（无 config.json） |
| MAU fork · hansaes | 0 DLC / 1 Depot，无主游戏密钥 |
| ManifestHub 快照 | 0 DLC / 2 Depot，无主游戏密钥 |

用户看到「收录 7/7」而拿到 0 个 DLC，必然认为是本工具的问题。

**结论**（本轮只做文案，对比表另行设计）：

- **界面明确区分「该源存在这个游戏的文件」与「该源的内容完整」**。前者是
  `probe` 能回答的，后者要下载并解析后才知道
- **主动告知「拿到的 DLC 少应换源」**。不等用户自己推断——他没有对比样本，
  唯一的参照系是「别人说能装两百个」，于是结论必然落在工具头上
- **清理全部「三源」措辞**（4 处）。源已扩至 7 个，而陈旧的数字会让用户
  怀疑界面与实际行为不符
- **未收录时补一句「若查询中出现过网络报错，可重新查询」**。三态化后
  `probeUnknown` 的源仍保留候选资格，但界面此前不体现这一点

**`reacquire()` 取首位源的写法留 `FIXME` 而非当场改掉**。它需要用户可选源
才能替代，而选源 UI 依赖尚未设计的对比表。留标注并附反例
（Kingdom Rush Vengeance 1367550：首位的 Hubcap 给 2 DLC，快照源给 4 DLC）
比仓促改成另一种写死顺序更诚实。

**该反例同时推翻了「Hubcap 恒为最优」的隐含假设**——设计对比表时不得写死
任何源的优先级。

## 2026-07-30: Hubcap 不参与自动试下载，额度消耗权交给用户

**背景**：为解决上一条，决定进入游戏页时对各源做「试下载」，解析出实得 DLC
数以供对比。但 Hubcap 是认证型源，**调用消耗用户自己的 API 额度**（凭据默认
7 天，网页端额度是 API 的 4~60 倍）。

把它纳入自动试下载，等于每次浏览一个游戏就替用户花掉一次额度，而用户可能
只是看看。

**结论**：

- **6 个 GitHub 源自动试下载，Hubcap 单列并需用户主动点击**。额度消耗权
  必须在用户手里
- **Hubcap 在界面上不进对比表的同一栏**。若与「64 DLC」并列而自身为空格子，
  视觉上会输给有数字的源，用户很可能因此绕开实力最强的源。改为单独一行 +
  一句事实陈述（「通常收录最全，但调用消耗你的 API 额度」）
- **不因此给 Hubcap 写死最高优先级**。Kingdom Rush Vengeance 的反例证明它
  并非恒优
- **试下载产物应缓存复用**（拟 `cache/trial/<appID>/<源名>.lua`，与权威留存
  `packages/` 分开，TTL 取短）。试下载拿到的就是完整 lua，用户选定源后可直接
  部署，零二次请求——这使「等一轮试下载」换来的不只是对比表，还有免下载安装

**本条为设计决策，尚未实现。** 记录在此以免施工时重新纠结额度问题。

**已于 2026-07-31 实现并实机验证**，见下方「试下载对比表落地」一条。

## 2026-07-31: 源生态维护是本项目的核心长期任务，而非一次性配置

**背景**：这是一条职责层面的认识，需要在此明确，因为它决定了将来的工作重心
分配，而错配的后果要很久才显现。

从三层解耦的结构出发：

```plain
在线仓库 → 风兔盒（把文件放对位置）→ OpenSteamTool → Steam
```

OST 是**可独立运行的存在**，与本工具完全解耦——用户手动把 lua 丢进
`config/lua/` 同样能用。且 OST 能自主下载 manifest（三级回退，见第一卷），
故合格的源只需提供 `addappid` 密钥与 `setManifestid` 的 GID 两串文本。

**推论**：本工具的价值不在「部署」这一步——那一步用户手动也能做。价值在于
**把「获取一份内容尽可能完整的 lua」这件事的成本降到足够低**。而这件事的
上限完全取决于源的质量与数量。

**结论**：

- **长期、持续地寻找、实测、收录清单源，是本项目的核心任务之一**，其优先级
  不低于功能开发。功能做得再完善，源贫瘠则用户仍拿不到 DLC
- **源的质量必须以实测数据判断，不以分支数或口碑判断**。已有两处反例：
  ManifestHub 快照源的广度是 MAU 的 15 倍而单游戏覆盖更少；Hubcap 在
  Kingdom Rush Vengeance 上反而不如快照源。这类判断只能靠逐个游戏实测
- **新源的接入成本已经很低**，这是「解析器只认扩展名与内容结构、不认文件名」
  这一旧设计的红利——MAU 形态的三个 fork 零解析改动即可接入。收录新源时应
  优先考察它是否落入已支持的形态，落入则几乎零成本

**由此浮现的架构议题**（未拍板，留待后续）：

源列表当前硬编码于 `defaultRepoSources()`，新增源必须改代码并重新发版。若源
生态维护确实是持续任务，这个形态迟早成为瓶颈——发现一个好源要等下一个版本
才能给用户用。两个候选方向：

1. **界面提供自定义源入口**。v2.0 目前没有（见「内置源列表按名称合并」一条），
   用户无从手动添加。成本低，但要求用户自己知道有哪些源可用
2. **源列表可远程更新**。能即时推送新源，但引入了「配置来自网络」的信任问题，
   且与本工具「不内置任何共享凭据」的原则需要仔细对齐

**倾向先做 1**。它不改变信任模型，且能让愿意折腾的用户自行接入新源，同时为
方向 2 积累「哪些源值得内置」的实际反馈。

## 2026-07-31: 试下载对比表落地，源选择权交还用户

**背景**：承接上方「收录与有用分离」与「Hubcap 不参与自动试下载」两条设计
决策，本轮实现并实机验证。

**实机数据**（MHW 582010，2026-07-31 00:08~00:11）：

| 源 | 结果 | 耗时观察 |
| :--- | :--- | :--- |
| MAU | 64 DLC / 2 Depot | 并发批次内完成 |
| MAU fork · tymolu233 | 63 DLC / 2 Depot | |
| MAU fork · hansaes | 0 DLC / 1 Depot | |
| ManifestHub 快照 | 0 DLC / 2 Depot | |
| MAU 镜像 | unsupported（无 config.json） | |
| MAU fork · bingyu50 | unsupported（无 config.json） | |
| Hubcap（手动触发） | **200 DLC / 8 Depot** | 单独请求 |

全源试下载耗时约 **41 秒**。汇总正确给出「4 个源可用，最高 64 个 DLC（MAU）」。
用户手动试 Hubcap 后选它入库，日志确认走的是缓存复用路径而非二次下载。

**落地时的实现结论**：

- **`trialOne` 复用 `DownloadFromRepo`**，不自行实现下载与解析。否则会出现
  第三条解析路径（已有在线与本地导入两条），三条路径的行为差异迟早表现为
  「对比表说 64 个，装上只有 60 个」这类无从排查的问题
- **缓存连 `GamePackage` 一起存**，不只存计数。这使用户选定源后零网络请求——
  缺了这一环，试下载就只是让工具变慢，用户有充分理由抱怨
- **缓存仅存于进程内，不落盘**。落盘要额外处理失效、清理、与 `packages/` 的
  语义区分三件事，复杂度远超收益。TTL 取 30 分钟：太长会让用户按几小时前的
  数据选源，太短则页面来回切换时反复重下
- **`TrialOneSource` 与 `TrialSources` 分成两个方法，不加「包含认证源」开关**。
  开关式设计下前端一旦传错参数就会静默消耗用户额度，而额度不可退还。两个
  方法使「花额度」必须由一次明确的调用表达
- **`summarizeTrials` 用严格大于比较**，并列时保留配置顺序在前者。使推荐结果
  稳定可复现——同样的数据两次刷新给出不同推荐，会让用户怀疑数据不可信
- **汇总字段名为 `BestSource` 而界面只说「实得最多」**。「最好」是价值判断，
  本工具没有依据做这个判断；数量多不等于质量高（KRV 反例）
- **`reacquire` 不再自动选源**，改为展示对比表。既然最优源因游戏而异，任何
  固定顺序都是错的

**三种「没结果」在界面上以左边框颜色分家**：可用（强调色）、仅本体（警示色）、
不可用（灰并降透明度）、网络失败（红）、未试取（虚线）。用颜色而非图标是因为
它不占宽度，且在密集列表中更易形成整体印象。

**未解决**：41 秒的等待偏长。当前靠缓存与免二次下载摊平，但首次进入陌生游戏
仍要等满。可选的优化方向是「先出 probe 结果占位，试下载结果逐条替换」，但那
需要事件推送与前端增量更新，留待 UI 重构一并考虑。

## 2026-07-30: PowerShell 脚本一律纯 ASCII，不靠 BOM 兜底

**背景**：`release.ps1` 初版含中文注释与中文输出，以无 BOM 的 UTF-8 落盘。
在 Windows PowerShell 5.1 下直接解析失败：

```plain
所在位置 build\release.ps1:13 字符: 22
+     [string]$Version,
+                      ~
“,”后面缺少表达式。
字符串缺少终止符: '。
```

报错行号（13）与真正的问题位置（101 行的中文字符串）**完全无关**，这是该
故障最具误导性的地方——照报错去看 `param` 块永远找不出问题。

根因：**Windows PowerShell 5.1 读 `.ps1` 时默认按 ANSI（zh-CN 下为 GBK）
解释**，除非文件带 UTF-8 BOM。UTF-8 编码的中文被按 GBK 误读后，可能凑出
反引号、单引号等语法字符，从而吞掉字符串终止符，使后续整块文本的解析全部
错位。

**结论**：

- **本项目的 `.ps1` 一律只用 ASCII 字符**，注释与输出全部英文
- **不采用「加 BOM 保留中文」的方案**。加 BOM 能解决本机问题，但脚本的
  编码约束从此成为隐性前提——任何编辑器「另存为 UTF-8」（多数默认不带 BOM）
  都会使其重新损坏，而报错依旧指向错误的行号。纯 ASCII 则不存在可被破坏的
  前提
- 该约束**只针对 `.ps1`**。Go 源码与 Markdown 文档继续使用中文注释——
  Go 编译器与 Markdown 渲染器都明确以 UTF-8 读取，不存在同类歧义
- 脚本首部注明此约束及其原因，避免日后有人「顺手把提示改成中文」

**校验方式**（施工时验证，不入库）：读取文件字节确认无 >127 的值，
再以 `[scriptblock]::Create` 解析全文——它完整解析但不执行任何语句，
正是「只验语法」所需。不用 `Parser::ParseFile`，其 `[ref]` 参数在
`-File` 模式下行为不稳。

## 2026-07-30: 补齐三个元信息方法，版本号编译期注入且外链限定 http(s)

**背景**：`CheckUpdate` / `OpenURL` / `GetAppVersion` 自前端完工起便挂在设置页的
`TODO` 上，是 v2.0.0 发布前最后一块缺口。三者与 DLC 清单管理无关，故新开
`app_meta.go` 承载，不再堆进已逾 1170 行的 `app.go`。

**结论**：

- **版本号经 `-ldflags -X main.appVersion=` 注入，默认值 `dev`**。硬编码字面量
  必然出现「改了 tag 忘了改代码」的偏差，而这种偏差在用户报障时会把排查引向
  错误的版本。前端也不另存一份，一律取 `GetAppVersion`
- **开发构建跳过版本比对**。`dev` 与任何版本号都无法比较大小，强行比出结果
  只会在开发过程中反复弹出无意义的更新提示
- **`OpenURL` 只放行 http 与 https**。`BrowserOpenURL` 在 Windows 上最终交给
  `ShellExecute`，它会执行 `file:` 指向的程序、按注册表处理任意自定义协议。
  前端目前只传常量链接，但这个方法一旦存在便是通用出口，日后若有人把用户输入
  或清单源返回的字段接进来，未加限制的实现就成了任意程序启动器。打开本地目录
  的诉求已由 `OpenDataDir` 单独承担，故无需放行文件路径
- **`CheckUpdate` 返回 `error` 而非 `OperationResult`**。检查更新失败是常态而非
  异常（国内访问 `api.github.com` 经常直接超时），前端据此按「暂时查不到」就地
  提示，而非弹错报为操作失败——弹错会让用户误以为工具坏了
- **用 `/releases/latest` 而非 `/releases`**。前者只返回一条且自动跳过 prerelease
  与 draft，正是「稳定版更新提示」需要的语义
- **不做结果缓存**。这是用户主动点击的操作，缓存反而会让「我刚发了新版怎么还
  提示是旧的」变成新的困惑来源
- **不引入 semver 库**。版本号形态完全由自己掌握，恒为 `x.y.z` 三段数字，
  为一处比较拉进一个依赖不划算。自实现按点分段比数值，段数不等时缺失段视为 0
- **`ReleaseNotes` 须按纯文本渲染**。内容来自外部，注入 `innerHTML` 等于把仓库
  写权限变成 XSS 入口
- **`GetReleasePageURL` 由后端提供**而非前端存常量。两处各存一份，改域名时必漏其一

**与发布流程的配合**：实际发布顺序是「蓝奏云先行，GitHub Release 收尾」，故此处
一旦报出新版本，安装包必然已经就绪——这正是选择 GitHub 作为版本信息源的原因，
它天然晚于蓝奏云。该因果关系已写进设置页的说明文案。

**已知局限**：`compareVersions` 把 `2.0.0-rc1` 判为与 `2.0.0` 相同而不提示更新。
若日后真的发布预发布版，应改用完整 semver 实现而非在此打补丁——预发布版的
排序规则远比看上去复杂。

## 2026-08-01: 令牌改名走别名过渡，第 1 步不动任何调用点

**背景**：UI 宪法把令牌重新命名（`--color-bg-elevated` → `--color-surface` 等），
而旧名在 12 个 `.vue` 文件里有调用点（`--color-bg-hover` 另有 6 处）。
施工第 1 步的定义是「样式拆分 + 令牌落地」，若同时改名就要一并动这 12 个文件。

**结论**：**第 1 步只换取值，不换名字。** 旧名保留为指向新名的别名，
集中在 `styles/tokens/legacy.css`，标注 `@deprecated` 与逐项迁移映射。

- **界面立刻变成冷紫调，而调用点一行不改**。视觉效果与代码改动量在此解耦，
  第 1 步因此真正做到了「改坏了只需回退一个 commit」
- **调用点迁移随第 4 步逐页执行**，与「每页一个 commit」的既定节奏合并，
  不额外产生一轮全局替换。全局替换的 diff 会大到没法 review，
  而 review 不了的 diff 等于没 review
- **时长令牌的映射刻意不是一一对等**：`--duration-base`（200ms）映到
  `--dur-fast`（160ms）而非同名的 `--dur-base`（240ms）。因为 v1 按组件类型
  分档、新令牌按位移距离分档，原先用到 200ms 的地方绝大多数是小位移。
  这条若不写下来，第 4 步迁移时必然有人按名字对应而把动效整体拖慢
- **`legacy.css` 整体删除而非逐条删**，删除前 grep 确认无残留。
  留着几条孤立别名比留着一整个标注清楚的文件更容易被遗忘

**推广**：这套「改值不改名、别名过渡、随页迁移」的做法适用于任何令牌重命名。
关键在于让**视觉变更**与**调用点变更**落在不同的 commit 里——
两者混在一起时，一旦视觉出问题就无法判断是取值错了还是替换漏了。

## 2026-08-01: CSS 层顺序声明放 index.html，因为 Vite 会吃掉裸 @layer

**背景**：宪法第 11.3 节用 `@layer tokens, base, ui, domain, utilities;`
免掉特异性战争。第 1 步落地时按常规写在 `styles/index.css` 顶部。

**实测发现**：**Vite 的 `@import` 内联流程会把不含任何规则的裸 `@layer` 声明
整条抹掉。** 单独成 `layers.css` 再 `@import` 同样被吃掉。产物中 `domain`
一词完全消失。

**结论**：顺序声明写在 `frontend/index.html` 的内联 `<style>` 中。

- 它不经 PostCSS，Vite 不会改它
- CSS 规范规定层顺序由**首次出现**确定，内联样式表先于外链 CSS 解析，
  故此处必定是第一次出现
- 代价是层结构改动要同步两处，两边均已写交叉引用注释

**这个失效为什么危险**：完全静默——不报错、不警告、`vite build` 成功、
**产物哈希一字未变**。层顺序退化为「首次出现顺序」，而 `domain` 层在第 1 步
还没有任何文件，于是根本没被注册。问题要等到第 4 步业务组件开始用它、
覆盖关系乱掉时才暴露，届时排查方向会指向组件本身而非构建配置。

**推广到一条一般判断**：凡是「只声明不产生规则」的 CSS at-rule
（`@layer` 顺序声明、空 `@supports` 等），都要假设构建工具可能把它当空语句
优化掉。**必须验产物，不能只验源码。**

验证探针：`findstr domain dist\index.html` 须有输出——`domain` 一词只出现在
顺序声明里，是全项目最干净的探针。
