## 2026-07-30: 主游戏识别改取第一个 addappid，不再要求带密钥

**背景**：原判据为「第一个带 key 的 `addappid` 调用即主游戏」。该判据在 Hubcap
格式下成立——其主游戏行写作 `addappid(2399830, 1, "b1ea599f...")`。

但 GitHub 快照源（SSMGAlt/ManifestHub2）的主游戏行不带密钥：

```lua
addappid(2399830)                                    ← 主游戏，无密钥
addappid(2399831, 0, "320e0bcc...")                  ← 主 Depot
setManifestid(2399831, "4735635872933062882")
```

原判据会跳过 2399830 而把 Depot 2399831 认作主游戏。后果有两重：`MainAppID`
错误导致部署文件名与历史记录全部记错游戏；且 2399831 被消耗为主游戏后不再进入
`Depots` 列表，其密钥与 manifest 一并丢失。

**结论**：

- **改取第一个 `addappid` 调用作为主游戏，带 key 时一并记入 `MainKey`。**
  依据是「主游戏必须最先注册」这一脚本语义要求——生成脚本时本工具自身遵循它，
  OST 侧同样依赖此顺序，两种源格式均满足
- **不采用「主游戏无 key」作为判据**。快照源恰好如此，但这是其生成流程的巧合而非
  语义保证。以巧合为判据，等于把另一个源的格式细节固化进解析器
- 主游戏无密钥时部署器已有处理（输出单行 `addappid` 并记警告），行为与源文件
  原样一致，不额外补密钥

**留待验证**：MAU 路径的 `fallbackMainKey` 在主 AppID 无密钥时会挑一个 depot 密钥
顶替，其注释称「生成脚本要求主游戏那行必须带密钥，否则已装本体的游戏会崩」。
若该说法成立，则快照源路径也需同等处理；若不成立，则 MAU 那处属过度防御。

倾向后者——快照源那 6.2 万分支的主游戏行都不带密钥，若真会崩，社区早已发现。
但此判断**无实测依据**，`deployer_ost.go` 中「Steam 会在校验阶段直接崩溃」这句
亦未经验证。保持现状（不补密钥，只记警告）是保守选择：照搬源文件原样不引入
新风险，而补一个不属于主 AppID 的密钥，其后果同样未知。

## 2026-07-30: 收录检测采用三态，仅 404 可排除候选源

**背景**：`probe` 原返回布尔值，`narrowToHits` 据此排除「未收录」的源。而 HEAD
请求失败的原因不止「资源不存在」一种——超时、连接重置、5xx、429 都会落入
同一个 `false`。

大陆直连 codeload 的失败率相当高。实测 `git ls-remote https://github.com/alex47exe/LuaMan`
一次耗 21 秒后报连接失败、一次报 `RPC failed; curl 56 Recv failure`，而同一时刻
`raw.githubusercontent.com` 经 curl 可正常访问。原 `lookupTimeout` 仅 8 秒，远短于
实测的失败耗时。

`narrowToHits` 原有一层兜底：全部探测失败时返回全部候选。但**部分失败的情形没有
兜底**——若 A 源探测成功而 B 源恰好抖动超时，B 会被彻底排除，即便它实际收录、
且下载阶段的四级镜像链本可取回。表现为「明明有清单却提示需要本地导入」。

**结论**：

- **`probe` 返回三态** `probeHit` / `probeMiss` / `probeUnknown`。只有服务端明确
  回应 404 才算 `probeMiss`；超时、连接重置、5xx、429、403 一律为 `probeUnknown`
- **`narrowToHits` 只排除 `probeMiss`**，`probeUnknown` 的源保留候选资格，交由
  下载阶段的镜像链兜底。检测是优化手段，不该拥有否决下载的权力
- 认证型源的错误**全部视为 `probeUnknown`**。凭据失效、额度耗尽都与「该游戏有无
  清单」无关，判为未收录会误导用户去找别的源
- **`lookupTimeout` 由 8 秒放宽至 15 秒**。过短的超时会把「网络慢」大量转化为
  `probeUnknown`，虽有候选资格保留兜底，但每个未探明的源都要在下载阶段白走一遍
  四级镜像链，反而更慢
- 判定逻辑抽出为纯函数 `narrowByProbeResults`，不涉及网络，由测试覆盖五种组合。
  该逻辑的失效方式是静默的——被误排除的源不报错，只是永远不被尝试

## 2026-07-30: 收录检测加并发上限，源数量增长不再线性放大请求

**背景**：`probeAll` 原为全源无限制并发。源数量为 3 时尚可，增至 7 个后会同时
向 codeload 发出 6 个请求（第 7 个是认证型源，走自己的域名）。

同一 IP 的突发请求可能触发限流，而限流响应（429/403）在新的三态判定下算作
`probeUnknown`——该源随即要在下载阶段白走一遍四级镜像链。即是说，**并发过高
反而使总耗时变长**。

**结论**：

- **以带缓冲 channel 作信号量，并发上限取 4**。七个源分两批完成，最坏情形为
  两倍单次超时，仍在可接受的等待范围内
- 该上限与 `enrichPackageDLCs` 的 `maxConcurrent = 4` 一致。两处都是对同一批公益
  代理与 GitHub 端点的并发访问，取同值便于将来统一调整
- **不按源类型区分并发额度**。认证型源虽走独立域名、不与 codeload 争抢配额，
  但为此引入分组限流的复杂度换不来可感知的收益

## 2026-07-30: 内置源列表在升级时按名称合并，只增不改

**背景**：`defaultRepoSources()` 仅在配置中的源列表为空时回填（`normalize` 的
既有逻辑）。这意味着新版本增加的内置源对老用户完全不可见——其 `config.json`
已存有旧版的 4 个源，非空，故不触发回填。

而 v2.0 目前暂时不提供自定义源的界面入口，用户也无从手动添加。表现为「升级后新源没
生效」，且界面上看不出任何原因。

**结论**：

- 新增 `mergeNewBuiltinSources`，按 `Name` 匹配，把配置中缺失的内置源补入列表
- **只增不改，已存在的条目原样保留**。不覆盖 `Enabled` 与 `Token`：前者是用户
  明确表达的意愿（手动停用过某个源），后者是用户自行申请的凭据。二者若因版本
  升级被重置，表现为「设置莫名恢复默认」，而用户很难把这现象与升级联系起来
- **新源追加在末尾而非按内置顺序插入**。这一取舍偏向「升级不改变现有行为」——
  新源作为额外兜底加入，不顶替用户已经在用的路径。代价是老用户的源顺序与新装
  用户不同，但顺序仅影响尝试次序，不影响可用性
- 合并返回新切片，不就地修改传入的列表。`normalize` 在持有锁的路径上被调用，
  就地修改会让调用方难以判断自己的切片是否已被改动

**测试锁定四条**：补入缺失源、不覆盖 Token 与 Enabled、已是最新时不产生重复、
不修改传入切片。其中第二条是最需要防回归的——它的失效直接导致用户丢凭据。

## 2026-07-30: 该站时间戳按美东时区解析，内嵌 tzdata 处理夏令时

**背景**：Hubcap 的 `/user/stats` 返回的 `api_key_expires_at` 形如
`2026-08-03T15:50:50.528769`，**不带时区标识**。原实现 `parseMSiteTime` 三个
layout 全部走 `time.ParseInLocation(..., time.UTC)`，函数注释亦写明「按 UTC 处理」。

但该站 lua 注释头写的是 `EDT`，据凭据生成时刻反推亦与美东时间吻合。按 UTC 解析
会使算出的到期时刻偏早数小时。

**结论**：

- **改按 `America/New_York` 解析**，而非写死 UTC-4 或 UTC-5。美东行夏令时，
  夏季为 EDT(UTC-4)、冬季为 EST(UTC-5)，任一固定偏移都会在换季后产生 1 小时误差
- **必须 `import _ "time/tzdata"` 内嵌 IANA 时区库**（约 450KB）。Windows 无系统
  zoneinfo，不内嵌则 `LoadLocation` 失败。且该失败是静默的——代码会退回 UTC，
  与修复前行为相同，问题看似消失实则未解
- `LoadLocation` 失败时退回 UTC 而非 panic。到期时刻偏早数小时只是提醒略微提前，
  不值得让整个额度面板不可用
- 测试同时锁定 7 月取 UTC-4 与 1 月取 UTC-5，以此验证内嵌确实生效——只测一个
  季节的话，退回 UTC 的情形在冬季测试中不会暴露

**原「偏早约 5 小时」的记载不准确**。草稿依 UTC-5 推算，但 7 月属夏令时应为
UTC-4，偏差是 4 小时。此细节不影响修复方式，但记录在此以免后续复核时困惑。

**背景**：`DECISIONS.md` 已达 73KB、逾 1100 行、56 条决策。每次开工前通读的成本

  长期有效的事实依据，改动它的风险大于收益

  施工推进而变的内容基本都在其中
