## 2026-08-03: 搜索状态与请求生命周期移入 store，推翻「会话级临时数据」

### 背景

`SearchPane` 把 `term` / `results` / `searching` / `searched` 全放组件内 `ref`，
文件顶部注释写着「搜索结果不进 store：属会话级临时数据，无其他页面需要读取，
放在全局反而要额外考虑何时清理」。

实机推翻：切页即销毁组件，关键词与结果全丢。更要紧的是 `await searchGames(q)`
的 promise 会落到已销毁的实例上，**结果被静默丢弃**——用户以为搜索没生效，
实际是搜到了没人接。

那句注释的失误不在结论错，而在**只问了一个问题**：「有没有别的页面要读」。
漏掉的是「组件销毁时正在飞的请求怎么办」。判断一个状态该不该进 store，
读取方不是唯一的考量，**生命周期长度**同样是。

### 结论

新建 `stores/search.ts`，状态与请求都归它。组件只触发与读取。

不做「关键词 → 结果」的多组缓存：搜索是一次性动作，用户回到本页要的是
「上次那一屏」，不是历史记录。多组缓存要额外回答何时失效，收益却只有
重复搜同一词时省一次请求。

`run()` 带请求序号，resolve 时比对是否仍是最新一发，过期响应丢弃。界面虽然
同时只允许一次搜索（按钮禁用），但那是**表现层的约定，正确性不该依赖它**
——回车键、日后可能加的搜索历史点击都可能并发触发。

原注释保留在文件里并标注已被推翻，避免有人日后又搬回去。

## 2026-08-03: 搜索状态改四值枚举，因为两个布尔容不下「失败」

### 背景

原实现用 `searching` 与 `searched` 两个布尔表达状态。而 `searched` 只在成功
路径置真——失败时它仍是 false，页面于是退回**初始空态**：用户刚点过搜索，
看到的却是「还没搜过」的样子。

错误此前只进 toast。toast 是瞬时的，切页回来连「刚才失败过」都无处可查。

两条合起来才是「搜索失败体验差」的结构性根源：不是文案没写好，是
**没有一个地方能承载「失败了」这个状态**。文案无处可落。

### 结论

改为 `SearchStatus = 'idle' | 'searching' | 'done' | 'failed'`，并给
`errorMessage` 一等地位。

枚举的价值在于**强制每种情形都得有个名字**。并列布尔的组合空间里，总有几个
组合没人给它取名，而那些无名组合就是缺陷的藏身处。

空态判据改用 `isEmptyResult`（仅 `status === 'done'` 时成立），显式排除
searching 与 failed——这两种情形 `results` 同样为空，只看长度就会在尚未查明
时断言「没找到这个游戏」。与 08-03 修的状态 C 误报同一形状。

失败时不清空上一轮结果：用户可能只是想再搜一次，把已有内容擦掉等于惩罚了
一次网络波动。错误提示与旧结果同屏并不矛盾——前者说「这次没成」，后者标着
自己属于哪个关键词（`executedTerm`）。

## 2026-08-03: 「切页不中断」的文案放在进行中，不用 toast

### 背景

请求生命周期移出组件后，「切页不会打断工作」成了事实，但用户不知道。
需要一个告知方式。

### 结论

搜索期间在搜索栏下方显示一行旁注：「正在搜索，切到其他页面不会中断，
回来还在这儿。」非搜索期间不显示。

不写进静态说明段：**没人会在没疑问的时候记住一条承诺**。这句话要解决的是
用户此刻正犹豫「能不能走开」，只有那一刻它才有意义。

不用 toast：toast 的时机恰好相反，是事情发生后才弹。而这里要的是**事情正在
发生时**持续在场。

视觉重量刻意低于结果本身（`--color-text-dim` + `--text-sm`）——它是陪伴而非
主角。同理，失败提示不用饱和主色：按宪法 4.1 主色只留给「下一步该点的那一个
东西」，而失败提示旁边没有可点的东西，重试入口是上方那个搜索按钮。

## 2026-08-04: 全局文件拖放防线，因为 WebView2 会被拖入文件弄崩

### 背景

实测发现，不论 `wails dev` 还是 `wails build` 的发行版，都能把任意文件拖进
窗口。症状分两种：

- 拖到 `DropZone` 以外的任何地方：绝大部分文件静默，但会闪一个 Windows
  透明弹窗（开了就马上消失）
- 拖文本类文件：额外唤出 Edge 原生的文本查看器窗口，**其中某些按钮点击后
  会让 WebView2 崩溃，宿主进程一并倒掉**

即用户拖错位置就能弄崩盒子。而这条路径**绕过了本工具的全部校验**——
`DropZone` 只认压缩包，可它管不到自己以外的区域。整个界面除了那一块之外，
处处都是没设防的入口。

`DropZone` 顶部原有注释已记着「必须对 dragover 调用 preventDefault，否则
WebView 会把拖入的文件当作导航请求直接打开」。**这个认知早就有了，只是当时
只在自己那一块落实。** 局部正确不等于全局安全。

### 结论

新建 `guards/fileDropGuard.ts`，在 window 捕获阶段挡掉 `dragover` 与 `drop`
的默认行为，`main.ts` 于 `mount()` 之前装上。

两个事件都要挡：只挡 drop 不挡 dragover，WebView 在 dragover 阶段就已接管，
drop 根本不会派发到页面上；只挡 dragover 不挡 drop，文件仍会被当导航打开。

用捕获阶段而非冒泡：安全兜底不该依赖别处的实现细节，即便将来某处组件写了
`stopPropagation` 也要先于它执行。

不影响 `DropZone`：它的 handler 在冒泡途中先跑，事件到达 window 时文件早已
交给业务逻辑。此处挡的不是「事件传递」，而是「浏览器接管」。

装在 mount 之前：挂载后才装会留下窗口期，而启动瞬间用户就能拖文件进来。
这类兜底没有「概率很低所以无所谓」的说法——它的代价是整个进程倒掉。

**方向上的取舍**：白名单优于黑名单。列举「哪里能拖」是有限且可穷尽的，
列举「哪些文件类型危险」永远列不完。

### 附带认知

开发模式下可用右键唤出 Edge 原生菜单（刷新、返回、打印、开发者工具），
发行版不能——这是有利的，方便调试且不泄漏给最终用户，无需处理。

## 2026-08-04: 互斥状态由单一枚举裁决，不靠多组判据碰巧不重叠

### 背景

08-03 修状态 C 误报时，用的手法是「往每个判据上补排除条件」。那治好了
「状态 C 何时该出现」，却漏了另一半——**状态 A 是独立的 `v-if`**，与状态
B/C 那条 `v-if / v-else-if` 链互不知情。

两条链都为真时**两个状态同时渲染**。实测点「重新获取清单」后可见源对比表
底下跟着一段「本地没有这个游戏的清单内容」，点「取消」后对比表收起，那段
错文案孤零零留在原地。

这是 08-03 那次修复**自己留下的**缺陷：修好了一处判据，没注意到判据是分散的。

### 结论

引入 `GameViewState = 'package' | 'loading' | 'sources' | 'noPackage'`，
由一个 computed 按优先级裁决，四个分支合入同一条 `v-if / v-else-if / v-else`
链。

**判据分散在模板里就无法保证互斥**：每加一个状态，都得指望作者记得去改另外
几处不相邻的条件。改成单一枚举后，「同时出现两个」在结构上不可能，而非依赖
作者的记性。

顺序即优先级，写在注释里：pkg 在手 → 正在读留存 → 未入库或主动换源 →
确认无留存。

### 顺带保住的类型收窄

模板判据从 `v-if="pkg"` 换成枚举比对后，vue-tsc 报 `pkg.dlcs` 可能为 null
——原先那个 `v-if` 顺带做了类型收窄，换掉就没了。

**没有用 `pkg!` 糊过去。** 那是把「此处一定非空」这个理由从代码里抹掉，只留
一个感叹号；日后若 viewState 的判据改动，感叹号不会报错，而问题会静默出现。
改为新增 `activePkg` computed 显式表达该关系，模板用它作判据，收窄与互斥
一并成立。

**类型报错是有价值的信号，不该消音。** 它当时指出的正是「这个等价关系现在
只存在于人的脑子里」。

## 2026-08-04: 详情与留存并发取，读取态不该被无关请求撑长

### 背景

`load()` 原先是先 `await getGameDetail()`，再读留存清单。于是读取态
（「正在读取本地清单…」）要挂满**整个详情请求**的时间——即便留存清单就在
本地、即便详情早已缓存。

实测在库页来回切两个已入库游戏时，表现为读取态疯狂闪烁。

### 结论

改 `Promise.all` 并发。留存通常先回（读本地文件），状态 B 直接就位，读取态
几乎不可见。

**这两件事本无依赖关系，串联只是因为写在同一个函数里的先后位置。** 顺序
不是设计出来的，是打字打出来的——而它产生了可观测的体验后果。

一般化：凡「进行中状态」的持续时间被无关请求撑长，先问那两个请求是否真有
先后依赖。

## 2026-08-04: 进度事件的监听必须早于触发它的操作

### 背景

`GamePane` 的 `EventsOn('download:progress')` 注册在 `await load()` **之后**。
而未入库游戏的 `load()` 会走 `lookup()`——真下载并解析各源，首次实测可达
41 秒，而 `download:progress` 恰恰是这段期间推送的。

等它跑完才装监听器，等于**首屏那 41 秒里一条进度都收不到**，`progressText`
始终为空。

已知残留清单里「试下载首次 41 秒」体验差，成因不只是慢，是**慢且没有任何
反馈**。「进度可见的等待不叫等待，叫围观」——而最需要围观的正是最慢的第一次。

### 结论

注册移到 `load()` 之前，`onMounted` 不再是 async。

一般化：**事件监听的注册必须早于任何可能触发该事件的操作**，包括同一函数里
写在前面的 await。这条在「注册与触发写在同一个生命周期钩子里」时最容易违反，
因为看起来它们是一起发生的。

## 2026-08-04: 待落盘的改动必须记下它属于哪个清单包

### 背景

`useDlcSelection` 用 800ms 防抖聚合勾选后落盘。原有的丢失防护只在
`onUnmounted` 里：`if (syncState.value === 'pending') void flush()`。

两个问题。

**其一，那条防护覆盖不到主路径。** 库页是 master-detail，`PaneTransition`
刻意复用实例（宪法 5.2），侧栏换游戏**根本不触发 `onUnmounted``**。而
「勾一下就切走」恰恰走这条路：

1. 用户在游戏 A 勾一个 DLC，`markDirty()` 排下 800ms 落盘
2. 200ms 后点侧栏换到游戏 B
3. `watch(appID)` 把 `pkg.value = null`，`watch(pkgRef, …, sync)` 随即清空
   `selected`
4. 800ms 到点，`flush` 读 `pkgRef.value` 已是 null，`if (!pkg) return`

游戏 A 那次勾选就此丢失，而界面在点击瞬间就乐观显示成勾上了。**宪法 3.3
主推的主路径，恰好是防护没覆盖的那条。**

**其二，`void flush()` 并不「立即」。** 查 `@vueuse` 的 `debounceFilter`
实现（`_clearTimeout(timer)` 接 `timer = setTimeout(...)`）确认：再调一次防抖
函数是「清掉旧计时器、重设一个新的」，即又等 800ms。注释写的「立即冲刷」
与实际行为不符。它没丢数据纯属侥幸——`setTimeout` 不随组件销毁取消，闭包里
的包引用还活着，那笔改动最终仍会发出，只是比预期晚。

### 结论

新增 `pendingPkg` 记录待落盘改动**所属的清单包**（非响应式，只做归属判定）。
三处出口各自都要能把改动交出去：防抖到点、换包、组件卸载。

记「属于哪个包」而非只记一个 dirty 布尔：防抖窗口内可能已经切走游戏，届时
必须分辨这笔改动是给谁的。用对象同一性比对，比存 appID 更直接——落盘调用要
的正是这个包本身。

拆出两个落盘函数：

- `syncActive`：反馈到 `syncState`，用于「用户正在看着的那个包」
- `syncDetached`：**不碰 `syncState`**，用于补交已经切走的包

后者不反馈状态的理由：此刻 `syncState` 已经归属界面上的另一个游戏，往里写
「正在同步」会把 A 的进度显示在 B 的页面上——那是拿一个状态承载两个游戏的
处境。但失败仍要 toast，因为落盘失败必须让用户知道，否则界面显示的勾选与
实际部署不一致。

防抖回调加归属校验（`pkg !== pendingPkg` 即 return）：窗口内切过游戏的话，
改动已由 `watch` 补交完毕，此处再跑一次会拿当前包配上当前勾选重复部署一遍。

`restore()` 也要清 `pendingPkg`——它是「读回已有状态」的语义，不产生待落盘
改动。漏掉会让上一轮的归属标记搭便车，把刚还原的集合当成用户的新改动。

一般化：**状态可以随界面切换归零，但已经答应用户的写入不能。** 凡「延迟执行
的写入」，都要问「执行时上下文是否还是当初那个」。

## 2026-08-04: 权威数据一律问后端，缓存只回答伴随刷新的问题

### 背景

实测：取消勾选某个 DLC 后立刻切到另一个游戏，再切回来，被取消的那个**仍
显示为勾选**。而磁盘上的 lua 与 `history.json` 都是对的。

`loadStored()` 里这一行是根源：

```
const record = libItem.value?.record ?? (await findHistory(appID.value))
```

`libItem` 来自 `library` store，而那是**缓存**——只在 `LibraryShell` 挂载时与
入库/卸载后刷新，库页切游戏不刷，勾选落盘也不刷。原实现拿 `findHistory` 当
兜底想省一次跨边界调用，可缓存命中时兜底永远轮不到。

**该缺陷只在取消方向可见。** 缓存存的是「上次刷新时的状态」，勾选方向上旧值
恰好等于正确值，症状被完全掩盖。

### 结论

勾选集合一律 `await findHistory(appID)`，删掉缓存那一层。

判据：**缓存可以回答「这游戏在不在库里」——那种变化必然伴随一次刷新；
不能回答「用户选了哪些」——那种变化不伴随刷新。** 省一次本地调用换不来这个
风险。

另补落盘后的库刷新（`useDlcSelection.refreshLibrary`）：部署改变 DLC 数与
安装时间，而侧栏条目的「N 个 DLC」、库概览统计、状态 C 的计数都读 library
store。不刷新则数字停在旧值且不报错。

放在 `useDlcSelection` 而非组件里：此处是唯一知道「落盘刚刚成功」的地方
——`syncDetached` 压根不动 `syncState`，组件侧观察不到它。刷新失败只静默，
缓存陈旧比落盘失败轻得多，不该盖掉后者的错误提示。

### 一条被推翻的排查判断（长期有效）

先前从「lua 含该条目而 history 不含」推出「两次部署抢跑」，方向是错的。

后端 `Record` 复制切片、整条覆盖，与 `Deploy` 同源同参，**不可能只错一半**
——这一点当时就足以排除写入侧，却被拿去佐证抢跑假设。

**症状里的「不一致」未必来自两个写入者，也可能来自两个读取来源。** 排查时
先问「这两个数是谁读的」，再问「是谁写的」。

### 附带记录：验证方式本身要可靠

主人第二轮从「切回来显示已勾选」反推「history 含该 ID」，中间隔着这层缓存，
推断不成立。同一个现象在第一轮是直接查 `history.json` 得出的，两次证据强度
不同。

**报症状时要说清是「直接看到的」还是「推断出来的」**，否则排查方向会被
中间层污染。

## 2026-08-04: 给否定分支补排除条件不等于处理了那种处境

### 背景

`LibraryOverviewPane` 的真空态判据是 `!items.length && !library.loading`。
它规规矩矩排除了「还在扫描」——这一点是对的。

但被排除的那种处境**不会消失，它掉进了 `v-else`**。于是首次进入已安装页时，
统计页先以全 0 渲染出来（实测「闪一下数据统计页，DLC 数是 0」），扫描完成后
再翻成空态。

**空态的判据写对了，代价转移给了 else 分支。**

### 结论

补第三条分支：`v-if="loading && !items.length"` → 什么都不画的占位。

一般化：**三种处境就得有三条分支。** 给否定分支补排除条件，只是把那种处境
推给了 else，不是处理了它。写完排除条件要接着问一句「被我排除掉的那种情况
现在归谁管」。

占位刻意什么都不画（只给 `min-height` 防塌陷）：扫描通常几十毫秒完成，画
骨架屏或转圈反而制造一次可见的闪动。**留空这一瞬什么都不说，比说错要好。**

### 本轮同一形状出现三次

- 状态 A 判据：`!installed` 兼任「该摆出对比表」（08-03 修）
- 真空态判据：排除读取中却把它推给 else（本条）
- 勾选还原读缓存：只在取消方向出错（上一条）

三者都是「一个方向碰巧对了」，故都长期潜伏未被发现。**一个缺陷在某条路径上
碰巧表现正常，是它能长期存活的原因，而不是它不严重的证据。**

## 2026-08-04: 搜索请求期间锁住整排控件

### 背景

原实现在搜索期间禁用了「搜索」与「清空」两个按钮，但输入框仍可编辑。

### 结论

输入框一并 `:disabled="search.searching"`，禁用态样式与两个按钮同一档
（`opacity: 0.5`），让「整排都锁住了」读起来是一件事。

理由是符合直觉而非功能必需——store 侧的请求序号已经能正确处理并发改词。
**表现层的一致性与逻辑层的正确性各自独立成立，不能互相顶替。**
