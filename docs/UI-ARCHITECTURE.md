# 前端 UI 设计与架构

> 本文是表现层的**宪法**，与 `ARCHITECTURE.md`（整体架构）、`DECISIONS*.md`（决策记录）并列。
>
> 适用范围：布局骨架、设计令牌、动效规格、控件自绘范围、装饰体系、文案语气、
> 前端目录与依赖方向。
>
> **本文有权否决业务层提出的界面方案**——例如「加一个开关让用户调 X」若与
> 第 9 章的设置项纪律冲突，以本文为准。
>
> 三条项目铁律对 UI 的含义（继承自 `ARCHITECTURE.md`，此处仅重申）：
> 界面不呈现任何直接操作 Steam 的入口、不呈现注入器配置项、不呈现注入器安装向导。

## 0. 为什么需要这一章

v2.0 功能层已完工并实机验证，界面「能用但不精致」。翻新若只是逐页调样式，会
重复踩同一个坑：**视觉不一致的根因不是审美，而是缺少可执行的规格**。

现状体检（2026-07-31 实测）：

| 症状                       | 根因                                                                                                 |
| :------------------------- | :--------------------------------------------------------------------------------------------------- |
| 界面平、卡片浮不起来       | 无阴影令牌，`--color-bg` 与 `--color-bg-elevated` 仅差 7 个灰阶                                      |
| 字号不整                   | 九档手感取值的 rem 小数（0.72 / 0.75 / 0.76 / 0.78 / 0.8 / 0.82 / 0.85 / 0.92 / 1.25）               |
| 改一次视觉要动四个文件     | 全局共享类只有 `.btn` 一组，`.block` / `.hint` / `.actions` / `.meta-bar` 在各视图 scoped 里各写一份 |
| 按钮字体与正文不同源       | `.btn` 漏了 `font-family: inherit`，Windows 上回落到系统 UI 字体                                     |
| 深色主题被打穿             | `DlcList` 用原生 `checkbox`，设置页用原生 `input` / `select`                                         |
| 页面过渡「有动效但没逻辑」 | `translateY(6px)` 淡入淡出，方向上不表达任何空间含义                                                 |

令牌层（间距阶梯、圆角、时长、双主题、`prefers-reduced-motion`、
`content-visibility` 纪律）本身扎实，**保留并扩充，不推倒**。

一条对全局有效的认识：

> **「精致」不是加东西加出来的，是把不一致减光了剩下的。**

用户不会逐条去数圆角是否一致、间距是否成体系，但**任何一处粗糙都会被潜意识
记账**，攒够了就变成「这软件看着不太靠谱」。故抽公共层不只是为了好维护，
**它本身就是视觉提升的主体工程**。

## 1. 核心设计命题

> **「它好可爱，但一定很可靠。」**

这两个词是相反的视觉信号：可爱靠圆润、跳跃、意外感；可靠靠对齐、克制、
可预期。同一元素兼顾两者，结果必然两边都不到位——这正是许多工具「花里胡哨
但看着不敢信」的成因。

### 铁律一：可爱与可靠分工，不混用

> **可靠由「信息载体」独占，可爱由「非信息载体」独占。**

| 归属     | 元素                                                             | 规则                                                   |
| :------- | :--------------------------------------------------------------- | :----------------------------------------------------- |
| **可靠** | 数字、源名、AppID、路径、DLC 列表、状态文字、错误信息            | 严格网格对齐、等宽数字、字重克制、颜色只表状态不表情绪 |
| **可爱** | 圆角、留白节奏、动效、空状态、图标、装饰花纹、成功时刻、文案语气 | 允许圆润、允许有个性、允许一点点意外                   |

试下载对比表是最好的例子：**数字必须冷静地对齐（可靠），而它出现的方式可以
是灵动的（可爱）**。数字本身不需要变可爱，它「怎么来的」才需要。

这条铁律同时回答了「不喧宾夺主」——因为可爱从来没碰过信息本身，它抢不到主。

### 铁律二：可爱的投放时机只有两个

> **可爱只出现在「用户正在等待」与「用户刚刚完成」两个时刻。
> 用户正在做决定时，任何可爱都是干扰。**

依据：等待时用户闲着，有注意力接收情绪；完成时心情好，鼓励能被接住；
决策时注意力是稀缺资源。

对本项目的直接映射：试下载那 41 秒是投放可爱的黄金位置，而**对比表本身要
冷静**；部署成功那一刻是第二个位置。

### 铁律三：信任由「从不含糊」攒出来，不由视觉给出

界面再精致，一次含糊其辞的失败就掉一半信任。

**UI 重构中不得为了「界面干净」而删除详细信息，只允许折叠。**

项目现有设计已在这条线上（对比表说「实得 64 个」而非「7 个源收录」、
「是社区还没收录不是你操作错」的文案、脱敏诊断包）。故这不是需要新增的设计，
**而是需要在重构中确保不被弄丢的设计**。

### 铁律四：不降低世界的复杂度，只降低理解它的成本

术语照实写但给出口、错误说全但给动作、高级项保留但视觉下沉——都是这一条的
具体表现。

这与项目的三层解耦职责观自洽：**盒子从不假装 Steam 和 OST 不存在，
它只是让用户不必自己动手。**

## 2. 参照物：PCL2 的可借鉴与不可借鉴

PCL2（Minecraft 启动器）是「可爱又有实力」在国内工具软件里的成功先例，
其价值在于**证明了这两者能同时成立**。以下结论来自实测观察，非印象。

### 2.1 它的信任感来自「看起来是做完了的」

PCL2 界面并不华丽，配色朴素、布局不前卫。信任感的真正来源是**没有一处
未完成的痕迹**：所有卡片圆角一致、所有间距成体系、每个按钮都有 hover 反馈、
每个加载都有明确进度、每个错误都有具体原因。

### 2.2 值得借鉴的四条

| #   | 做法                                                                               | 对本项目的映射                      |
| :-- | :--------------------------------------------------------------------------------- | :---------------------------------- |
| ①   | **总在解释自己正在做什么**。下载时不是转圈，而是写明当前在下哪个文件、第几个、多大 | 直接适用于试下载 41 秒（第 5.5 节） |
| ②   | **错误信息极其诚实且具体**，从不说「操作失败，请重试」，并提供一键复制             | 强化诊断包引导（第 8.3 节）         |
| ③   | **文案有人味，但信息量不减**                                                       | 第 8 章文案规范                     |
| ④   | **动效密度高但从不阻塞**，且全软件共用同一套时长与曲线                             | 第 5 章动效令牌收敛                 |

第 ④ 条值得展开：PCL2 的「爽快」来自动效**统一**而非动效**多**。整个软件像一个
有固定脾气的东西在响应你，而不是十几个组件各自表演。

### 2.3 它最狠的一招：控件全部自绘

PCL2 用 WPF，但几乎未使用系统原生控件——复选框、下拉框、滚动条、输入框全部
自绘。结果是整个界面没有一处「破功」。

反之，界面里只要混进一个原生控件，精致感立刻塌掉：它带着操作系统自己的圆角、
配色和动效时长，与设计语言完全不同源。**用户说不出哪里怪，但会觉得
「这软件是拼出来的」。**

本项目当前正踩在这个坑上，故立为硬约束，见第 6 章。

### 2.4 不应借鉴的两条

**① 它的信息密度对本项目过高。** PCL2 面向有折腾意愿的 MC 玩家，设置页可以
铺满选项。风兔盒的目标用户含「完全不懂 Steam 目录结构」的人，同样密度会直接
压垮他们。本项目要的是**同样的诚实，但更少的同屏信息量**——靠渐进披露达成，
不靠删功能。

**② 它的俏皮文案偶尔会盖过信息。** 有些提示读完会心一笑，但没记住要干什么。
这是「不喧宾夺主」在文案层的同一个坑。

### 2.5 本项目相对 PCL2 的先天优势与风险

PCL2 用 WPF 自绘，动效需手写 Storyboard，圆角阴影都要自己拼。本项目是
WebView2 + CSS——内高光、同心圆角、`content-visibility`、可中断 transition
在 CSS 里都是几行的事，**达到同等观感的成本只需一小部分**。

但反过来：本项目**没有**「必须自绘所以想不一致都难」的强制约束，CSS 里偷懒用
原生控件太容易。

> **真正的风险不是做不到，是做一半。**

这是公共层必须先抽的根本理由：**共享类与共享组件是一致性的执行保障，
不只是为了少写代码。**

## 3. 三板斧骨架

```
+---------------------------------------------+
| 顶栏 TopBar（46px，frameless 拖动区）        |  <- 灵魂，结构不动
+--------------+------------------------------+
|              |                              |
|  侧栏         |        内容区                 |
|  Sidebar     |        Content               |
|  (240px)     |        (flex: 1)             |
|              |                              |
+--------------+------------------------------+
```

### 3.1 侧栏的统一语义

三页必须一致，否则三板斧就只是三个巧合：

> **侧栏回答「看什么 / 从哪进」，内容区回答「看到的是什么」。**

**侧栏永不承载最终信息，只承载「选择」。** 这条保证用户对侧栏形成稳定预期。

### 3.2 三页映射

| 页面       | 侧栏                                                         | 内容区                             |
| :--------- | :----------------------------------------------------------- | :--------------------------------- |
| **首页**   | 品牌标识 + 获取方式入口（在线搜索 / 本地导入）+ 运行状态摘要 | 对应入口的操作区与结果列表         |
| **已安装** | 全部已部署游戏（含外部清单），带筛选框，分两组               | 选中游戏的详情；未选中时显示库概览 |
| **设置**   | 子导航：外观 / 清单源 / 关于 / 调试                          | 对应小节                           |

**引导页（`SetupView`）不套三板斧**，保持独立全屏——它是一次性流程，
侧栏在此只会分散注意。

### 3.3 已安装页改为 master-detail 的收益

最大收益不是视觉，而是**「换游戏」不再需要往返**。

现状：从库进详情、看完退回、再进下一个，每次整页重挂载。
改后：切游戏只换右半边，侧栏列表与滚动位置保持不动。

这同时让「卸载后留在原页」那条既有决策（`DECISIONS` 缺陷④）落得更自然——
因为根本没有「原页」可离开，复位天然发生在内容区。

### 3.4 首页把本地导入提到侧栏的依据

这不是新决定，而是把既有决策落到视觉上。`DECISIONS` 已记：

> 「M 站网页端额度是 API 的 4~60 倍，故本地导入是一等入口，不是退路。」

而现状它躺在搜索页底部的折叠区，**视觉上就是个退路**。侧栏常驻使其与在线搜索
平级。

附带收益：侧栏那颗入口本身可充当拖放靶子，用户在任何入口下都能直接把 lua
拖进来。

### 3.5 已安装侧栏的三条约束

1. **必须可筛选**。装了上百个游戏时纯列表不可用。
2. **必须分组**：「本工具管理」与「外部清单」。外部清单项**不提供 DLC 编辑**
   （`DlcList` 已有 `readonly` prop，语义正好对上），且需明确标注来源不明——
   这关系到卸载时的外部声明约束（见 `DECISIONS` 07-28 实测三条硬约束）。
3. **未选中时内容区不得空白**。显示库概览：共 N 个游戏 / M 个 DLC /
   最近获取时间 / 冲突项警示。**空态是引导位，不是留白位。**

### 3.6 设置页拆侧栏

现状四个 block 一路往下滚。拆开后每屏只讲一件事，且：

- **「清单源」终于有自己的地盘**，PROGRESS 第 4 号议题（用户自定义源）有地方落
- **「调试」有地方放**诊断包导出与相关警示文案（第 8.3 节）

「设置项不够多所以显得空」不是问题——见第 9 章，本项目的设置页方向是
**少而准**。

#### 补注：实际落地为四节，与本节设想有两处差异（2026-08-01 第 4 步）

本节原设想侧栏四项为「外观 / 清单源 / 关于 / 调试」，实际落地是
**环境 / 清单源 / 外观 / 关于与诊断**。两处改动各有理由：

1. **补「环境」为独立首节。** 原设想漏了它，但 Steam 路径是整条部署链路的
   唯一权威（`DECISIONS` 07-27），且用户点进设置最常见的动因就是
   「哪里没配好」。故它排第一，且 `/settings` 默认重定向到它。

2. **「调试」并入「关于」。** 该节的全部内容是诊断包导出与两句警示文案，
   单独一屏会空得反常——而这与「设置项少是优点」是两回事：**一个小节空**
   和**整页设置项少**给用户的观感相反，前者像没做完。
   且它与版本号、日志路径同属「报障时要用的东西」，聚在一处更合用。
   若后续调试项增多再拆。

顺序即用户遇到问题的先后：环境不通则一切不可用；源决定能拿到什么；
外观是偏好；关于与诊断是出事时才来的地方。

### 3.7 游戏详情的归属（路由改动的关键）

详情**不再是独立页面**，而是渲染进「用户来的那个列表」的内容区：

- 从首页搜索结果进入 → 侧栏保留搜索结果列表
- 从已安装列表进入 → 侧栏保留已安装列表

收益：用户试了一个源不满意，**不必返回就能点侧栏的下一个候选游戏**；
「返回」几乎不再需要；卸载后的复位不影响侧栏上下文。

代价：路由需改为嵌套，`GamePane` 在两棵路由树下注册同一组件。
**这是本轮唯一的结构性改动，须单独一个可回退的 commit**（第 12 章第 3 步）。

### 3.8 窄窗口

侧栏在窗口宽度低于阈值时折叠为图标条，可手动展开。

**不做「自动隐藏」**——侧栏承载导航，消失会让用户失去方位。

窗口最小宽度需与 `main.go` 的 `MinWidth` 对齐确认，可能需调后端（第 13 章）。

### 3.9 内容区最大宽度

现状 `GameView` 限 860px 居中。三板斧下侧栏已占 240px，若内容区仍限 860，
宽屏下右侧会空出一大块。

**放宽至 1040px，保留居中。**

## 4. 设计令牌

### 4.1 色彩

**主色调为冷紫偏灰。深浅两套均不含纯白与纯黑。**

色偏必须小到**「说不出它是什么颜色，但一眼觉得比纯灰高级」**——一旦能看出
「这是紫色背景」就过了。饱和度约 8~12 度。

选冷紫而非暖褐或冷青的理由：它与既有粉调主色同源，配起来天然协调；
暖褐会偏「文艺」，冷青会偏「科技」，都离「可爱又可靠」更远。

```css
/* 深色（默认）
   --color-bg 需与 wails.json 的 backgroundColour 及 main.go 的
   BackgroundColour 保持一致，否则窗口创建到首帧之间会闪白。 */
--color-bg: #1b1a20; /* 冷紫底，替代原 #1e1e1e */
--color-surface: #232128;
--color-surface-2: #2a2731; /* 悬停 / 次级面 */
--color-border: #37343f;
--color-border-str: #4a4655;
--color-text: #eceaf0;
--color-text-muted: #a5a0b0;
--color-text-dim: #6f6a7c;

/* 浅色 */
--color-bg: #f4f2f8;
--color-surface: #fbfaff; /* 不用 #ffffff */
--color-surface-2: #edeaf4;
--color-border: #ddd8e6;
--color-border-str: #bcb5cc;
--color-text: #221f2a;
--color-text-muted: #5d5769;
--color-text-dim: #8b8499;
```

主色沿用粉调：深色 `#ff8fb1` / 浅色 `#e8628f`（既有取值，与冷紫底同源）。

#### 点缀色硬规则

为使「克制」可验真而非只是形容词：

> **每一屏，饱和主色只允许出现在「用户下一步应该点的那一个东西」上。**

一屏出现两个粉色按钮等于没有指引。这条同时服务美观与易用——**小白最怕的就是
不知道点哪**。

#### 状态色不共享主色

可用 / 仅本体 / 不可用是三种**事实**，主色是一种**引导**。混用会暗示
「粉色边框的源是被推荐的」，而项目铁律明令**不得写死源优先级**
（依据：Kingdom Rush Vengeance 1367550 上 Hubcap 只给 2 个 DLC，
快照源给 4 个）。既然逻辑上不写死，**视觉上同样不得暗示**。

故状态色独立成一组语义令牌，与 `--color-accent` 无关。

```css
/* 深色 */
--state-ok: #5fc9a3; /* 可用 */
--state-warn: #d9b268; /* 仅本体 */
--state-neutral: #79738a; /* 不可用（unsupported / miss） */
--state-danger: #e0757e; /* 网络失败 */
--state-wash: 6%; /* 整行淡染透明度（第 10.2 节） */

/* 浅色 */
--state-ok: #2f9a78;
--state-warn: #a8792a;
--state-neutral: #8b8499;
--state-danger: #c9505c;
--state-wash: 4%;
```

三条取值理由，都是长期有效的判断：

- **`ok` 用冷绿而非沿用既有 `#4ec9a0`**——后者偏青，在冷紫底上会显脏。
  状态色必须与底色同温，否则看起来像从别的软件里抠过来的。
- **`neutral` 刻意取自 `--color-text-dim` 邻域**，使「不可用」在视觉上等同于
  「一段被弱化的文字」而不是「一种状态」。它本就不需要被注意到。
- **`danger` 与主色粉调刻意拉开色相距离。** 两者若靠得太近，
  「饱和主色只出现在下一步该点的那一个上」这条会被误伤——
  用户会把一行失败误读为一个可点的推荐项。

**`--state-wash` 深浅不同取值**：浅底对淡染更敏感，同样 6% 在浅色下会显得
像选中态。这与第 4.2 节同属「双主题不能只换变量」。

#### `--color-raised`：凸起在面之上的那一层

```css
/* 深色 */
--color-raised: #3a3645;
/* 浅色 */
--color-raised: #fdfcff;
```

为什么需要它而不直接用 `--color-surface`：**深色主题下 `--color-surface`
比 `--color-surface-2` 更暗**，于是「凸起的元素放在次级面上」会得到
「凸起的东西比底更暗」——这在物理上不成立，观感就是没凸起。
浅色主题恰好相反，`surface` 本就比 `surface-2` 亮。

分段控件的滑移指示器正是踩了这个坑：浅色下看着正常，深色下几乎看不见。

**一般判断**：**凡是表达「层级关系」的颜色，都不能靠两个平级令牌的明暗
碰巧成立**——它在一套主题下对，在另一套下就会反。
必须抽成语义令牌由各主题自己给值。

`skipped` 状态**不分配颜色**，只用虚线描边——它表达「还没发生」，
给颜色就等于宣称它有结论（第 10.3 节）。

### 4.2 层级：内高光 + 极轻阴影

Aero 让人觉得精致的核心**不是半透明，而是顶边一道 1px 内高光 + 底部极轻
暗边**，模拟光从上方来，物体因此有厚度。成本极低、不掉帧，但立刻就不扁了。

大部分模仿 Aero 的实现只学了半透明，然后就变重了。

```css
--elev-0: none; /* 页面底层 */
--elev-1:
  0 1px 2px rgba(0, 0, 0, 0.2), /* 卡片 / 面层 */ 0 2px 8px rgba(0, 0, 0, 0.12);
--elev-2: 0 8px 32px rgba(0, 0, 0, 0.32); /* 弹窗 / 浮层 */
--hairline-top: inset 0 1px 0 rgba(255, 255, 255, 0.06); /* 深色专用 */
```

浅色那一半（缺它则第 1 步落不全令牌）：

```css
/* 浅色：内高光改为极淡内白 + 更轻的阴影，光的方向不变（仍从上来） */
--elev-1: 0 1px 2px rgba(40, 34, 58, 0.06), 0 2px 8px rgba(40, 34, 58, 0.05);
--elev-2: 0 8px 32px rgba(40, 34, 58, 0.14);
--hairline-top: inset 0 1px 0 rgba(255, 255, 255, 0.9);
```

**浅色阴影不用纯黑加透明度，用带紫的深色 `40,34,58`。** 纯黑阴影落在冷紫底上
会灰得发脏——这是浅色主题最容易露怯的一处，且极难被归因，
用户只会觉得「浅色模式没深色好看」。

层级分配：

| 层           | 令牌                                         |
| :----------- | :------------------------------------------- |
| 底层（页面） | `--elev-0`，无阴影                           |
| 面层（卡片） | `--elev-1` + `--hairline-top`                |
| 浮层（弹窗） | `--elev-2` + `--hairline-top` + 轻微放大入场 |

**浅色主题不能只换变量**：内高光在浅色下几乎不可见，须改为极淡的上方内阴影 +
略强的边框来表达同一层级关系。**这是双主题同等打磨的主要额外工作量所在。**

#### 阴影轻重的判定标准

> **截图缩到 30% 还能明显看出阴影，就是太重了。**

正确的程度是：轻到用户不觉得有阴影，只觉得卡片「是一块东西」。

### 4.3 字号阶梯

现状九档手感取值是视觉不整的直接来源。收敛为六档：

```css
--text-xs: 11px; /* 角标、图例 */
--text-sm: 12px; /* 元信息、提示 */
--text-base: 13px; /* 正文（桌面端 14px 偏大） */
--text-md: 15px; /* 区块标题 */
--text-lg: 19px; /* 页面标题 */
--text-xl: 25px; /* 数字强调、空态主文案 */
```

字重只用 `400 / 500 / 600` 三档。

具体替换随第 4 步逐页迁移执行——不定死的话，六个页面会各自拍板一次，
旧档就变成了新的旧档。

另九个值无归属——而第 4 步是逐页施工，六页会各自为这些值拍板一次，

控件走 ctrl、控件内元素走 inner、角标走 chip。这是视觉上的实质改进，
也是「同心圆角」这条规则第一次真正落地。

#### 时长的同类改判

| 位置                     | 账本方向              | 实际归                | 理由                                                                                                                                                                                |
| :----------------------- | :-------------------- | :-------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ConfirmDialog` 弹窗本体 | `--dur-fast`（160ms） | `--dur-base`（240ms） | `motion.css` 里 `--dur-base` 的注释**明确写着「侧栏换内容、弹窗入场」**，令牌定义自己就把弹窗入场归在这一档。账本那条「按名字对应会拖慢」的警告针对的是大部分小位移场景，弹窗不属于 |

**归档依据是语义，不是就近取整。** 六档令牌的定义本身是语义的
（角标／元信息／正文／区块标题／页面标题），按 px 距离归会把页面标题
塞进区块标题档，那是把层级关系算没了。

两个可对照的例子：

- `1rem`（16px）离 15 比离 19 近，且它在 `ConfirmDialog` 与 `DropZone`
  上都是**区块标题**，归 `--text-md` 恰好。
- `1.05rem`（16.8px）只比它大 0.8px，但那是 `LibraryView` 的 `h1`，
  是**页面标题**，必须归 `--text-lg`。

**遇到语义与本表冲突时以语义为准，并在此表补一行说明**——
表是为了让六页得出同一结论，不是为了让人机械套用。

`--text-xl`（25px）**无既有来源**，是新增档位，专供空态主文案与对比表数字强调
（第 10.2 节「数字放大加粗」的落点）。

迁移期判据：任一视图迁完后，其 scoped 样式里不应再出现 `rem` 字号字面量。
全量判据（六页迁完后）：

```
findstr /s /n rem; frontend\src\*.vue     须无输出
```

**所有数字强制 `font-variant-numeric: tabular-nums`**——对比表的核心动作是
纵向扫一列数字，字宽浮动会毁掉这件事。

### 4.4 圆角：同心圆角

苹果那种严丝合缝感来自一条几乎没人执行的规则：

> **嵌套元素圆角 = 外层圆角 − 内边距。**

卡片 12px 圆角、内边距 8px，里面的按钮就该是 4px，不是也随手写 8px。
不同心会让内外圆弧之间产生视觉缝隙，**那种说不出的廉价感就是这么来的**。

```css
--radius-card: 12px;
--radius-ctrl: 8px;
--radius-inner: 6px;
--radius-chip: 4px;
```

**禁止全圆胶囊按钮**——那是消费级 App 的语言，会削掉「有实力」。
大圆角服务可爱，但大到胶囊就变幼稚。

### 4.5 动效令牌

```css
--dur-instant: 100ms; /* 按下反馈、颜色变化 */
--dur-fast: 160ms; /* 内容区切换、指示器滑移 */
--dur-base: 240ms; /* 侧栏换内容、弹窗入场 */
--dur-slow: 360ms; /* 侧栏高度过渡、大位移 */

--ease-standard: cubic-bezier(0.2, 0, 0, 1);
--ease-decelerate: cubic-bezier(0.16, 1, 0.3, 1); /* 沿用既有取值 */
--ease-accelerate: cubic-bezier(0.4, 0, 1, 1);

--stagger: 24ms; /* 逐项错开步长，最多 8 项 */
```

**时长按位移距离分档，不按组件类型分档。** 小位移必须快，大位移才允许慢。

**执行时不得出现表外的值。** PCL2 的「爽快」正来自所有动效共用同一套脾气，
整个软件像一个有固定性格的东西在响应你。

### 4.6 间距

沿用既有 4px 基数阶梯（`--space-1` 至 `--space-7`），不改。它已在用且成体系。

## 5. 动效规格

参照 PCL2 实测行为拆成三个**互相独立**的层，各层时长不同。

这是「丝滑」的技术关键：**整体不是一个大动画，而是几个短动画错开。**

### 5.1 顶栏页签切换（跨页，最大动作）

| 层         | 行为                                                                        | 时长                             |
| :--------- | :-------------------------------------------------------------------------- | :------------------------------- |
| **顶栏**   | 不动。仅当前页签的指示条横向滑移到新位置                                    | `--dur-fast`                     |
| **侧栏**   | 旧内容淡出并轻微上移退场 → 容器高度过渡到新尺寸 → 新内容逐项淡入 + 轻微下落 | `--dur-base` / 高度 `--dur-slow` |
| **内容区** | 旧内容淡出（快）→ 新内容自上方短距离落入并淡入                              | `--dur-fast`                     |

侧栏逐项入场**错开 `--stagger`（24ms），最多前 8 项参与**，其余直接入场。

#### 两条设计意图

**① 内容区必须快于侧栏。** 内容是用户真正要看的东西，它先稳定下来，界面就显得
敏捷；侧栏慢一点反而衬出层次。

**② 错开上限 8 项是性能纪律，不是美学选择。** 若 200 条全参与错开，最后一条要
等 4.8 秒才出现——**动效就变成了卡顿**。

### 5.2 侧栏内选择切换（同页，中等动作）

侧栏**完全不动**，仅选中态指示器在两项之间**滑移**（不是消失再出现）。
内容区走一次快速淡入 + 6px 下落。

指示器滑移而非闪现，是为了让用户眼睛能跟住「选择从哪移到哪」。

### 5.3 元素级微动效（最小动作）

- 按钮按下 `scale(0.97)`
- 卡片悬停上浮 2px
- 试下载结果逐条落位时轻微一跳

### 5.4 三条硬规则

**① 必须回答「从哪来、到哪去」。**
弹窗从触发它的按钮位置放大出来，返回时缩回去；列表新行从它将占据的位置淡入，
而非从屏幕外飞入。**位置突变是最廉价也最让人晕的动效。**

现状 `translateY(6px)` 淡入淡出在方向上不表达任何含义，属于「有动效但没逻辑」。

**② 必须可中断。**
用户在过渡中点了下一个动作，新动作立即接管，不排队等前一个播完。

> **这是「丝滑」与「卡」的真正分水岭**——多数被认为动效卡的软件，
> 其实是动效不可中断。

工程落地见第 7.3 节：**位置/透明度过渡一律用 `transition`，
只有循环动画用 `animation`。**

**③ 缓动有方向。**
入场 `--ease-decelerate`（快速出现然后稳稳停住，显得敏捷可靠），
退场 `--ease-accelerate`（缓慢加速离开，不抢注意），
位移 `--ease-standard`。

### 5.5 试下载 41 秒的处理

**现状**：全源试下载约 41 秒（并发上限 4），首次进入陌生游戏必须等满。
这是 PROGRESS 已记的残留项。

**方案**：表格先出全部源的**占位行**，各行随结果返回**逐条就地替换**并轻微一跳。

依据：

> **进度可见的等待不叫等待，叫围观。**

这同时消掉了 PROGRESS 里那条体感残留——**两件事本就是一件事**，
UI 重构时一并做掉最省力。

**依赖**：后端需按源推送事件。现有 `download:progress` 已有雏形，
属功能层改动，列入风险表。

配合关系：**热气装饰在上方慢慢升，结果在下方一条条落定**，
两个动作方向相反、互不干扰（第 7.4 节）。

### 5.6 `prefers-reduced-motion`

既有全局规则保留，但需强化：

> **必须真正禁用位移类动效，不只是缩短时长。**

装饰类循环动画（热气）在此模式下**完全静止**（不是变快，是不动），
换成静态图形 + 文字进度。

部分用户会因前庭功能障碍而对动画产生不适，**这不是可选的润色项**。

## 6. 控件自绘范围

依据第 2.3 节：界面中混进任何原生控件都会让精致感塌掉。故立硬约束：

> **界面中不得出现任何未经完全接管的原生表单控件。**

### 6.1 当前欠账

| 位置           | 问题                                                        |
| :------------- | :---------------------------------------------------------- |
| `DlcList`      | 全部使用原生 `checkbox`，且可点区仅 13px                    |
| `SettingsView` | 原生 `input`（API key）与原生 `select`                      |
| 全局           | 滚动条已部分自绘（`::-webkit-scrollbar`），但未纳入组件体系 |

**深色主题下 Windows 原生下拉框会弹出白色列表，直接把主题打穿。**

### 6.2 需自绘并抽为公共原语

`UiButton` / `UiCheckbox` / `UiRadio` / `UiSwitch` / `UiInput` / `UiSelect` /
`UiTooltip` / `UiHelpBadge` / `UiScrollArea` / `UiProgress` /
`UiEmptyState` / `UiSegmented`

### 6.3 三条不可省略的实现要求

**① `:focus-visible` 必须自己实现。**
这是自绘的主要代价，**省掉就等于砸了无障碍**。

**② 可点区域不小于 28×28px**，视觉可以更小。
`DlcList` 那种密集列表尤其需要——现状原生 checkbox 只有 13px。

**③ 原生语义必须保住。**
`UiCheckbox` 内部仍是真 `<input type="checkbox">`，只是
`appearance: none` 后自绘视觉。

> **不要用 `div` + `role="checkbox"`** ——那样键盘、表单、读屏全部要手写，
> 且几乎必然做不全。

### 6.4 `UiSelect`：唯一真需要浮层的原语

- 用原生 `popover` 属性拿「顶层渲染 + 点外关闭 + Esc 关闭」，白捡三个行为
- 定位交给 `useAnchoredLayer`（约 60 行：`getBoundingClientRect` +
  `position: fixed` + 边界翻转）

**不引入 floating-ui。** 项目已定「不引 UI 组件库」（依据：可复用的仅按钮与
弹窗，却会把打包体积从约 100KB 推到 1MB 以上），而浮层场景只有下拉与 Tooltip
两个，10KB 依赖换 60 行代码不值。

**但需诚实记录**：若日后浮层场景涨到五六个，这个判断应当推翻。

**风险**：frameless 下浮层是否被窗口边界裁切，需实机验证一次（第 13 章）。

## 7. 装饰花纹体系

意象来源为 GochiUsa（项目名 kazeusa 的由来）。风格定为现代扁平，不复杂。

**用户读不出典故完全没关系。** 意象的价值不在「被读懂」，而在于**同源**——
所有花纹从一个来源长出来就天然一致，用户说不出为什么，但能感到
「这软件是一个人认真做的」，而不是素材拼的。这与自绘控件是同一个道理。

### 7.1 禁区（硬性）

按铁律一，花纹属非信息载体，**只能出现在信息不在的地方**。

**允许区**：

| 位置                                     | 花纹角色               |
| :--------------------------------------- | :--------------------- |
| 空状态（库为空、搜索无结果、未选中游戏） | 主视觉，可以最放得开   |
| 侧栏底部留白（品牌区下方）               | 常驻但极淡             |
| 引导页                                   | 一次性流程，允许最精致 |
| 详情页 hero 背后                         | 极淡，衬托封面         |
| 等待态（试下载期间）                     | 唯一允许动的地方       |

**禁区**：

- **试下载对比表背后** —— 它是纵向扫数字的地方，任何纹理都会干扰
- **DLC 列表背后** —— 同上，且行数多，重复纹理会晃眼
- **任何等宽字体区域**（AppID、路径、哈希）—— 这些字是要被复制的
- **错误与警示横幅背后** —— **会稀释紧迫感，这是信任的直接损失**
- **顶栏** —— 灵魂区，且它是拖动热区，装饰会让人误判可点

再加一条与「点缀色只出现一处」对偶的规则：

> **每一屏最多一处装饰主体。** 侧栏有了角落纹样，内容区就不再放；
> 空状态有了主视觉，四周就干净。

### 7.2 四种角色

花纹**不是「一张图到处贴」**——那样迟早为适配各种尺寸而变形走样。

| 角色                         | 形态                                       | 要点                                                         |
| :--------------------------- | :----------------------------------------- | :----------------------------------------------------------- |
| **微平铺** micro-tile        | 48~64px 无缝小图案                         | 元素要小且稀疏，密了立刻变「壁纸」                           |
| **角落纹样** corner ornament | 单个较大图形，从边角切出画面外，只露一部分 | **露出局部比完整摆中间高级得多**，因为它暗示画面之外还有东西 |
| **分隔纹** divider flourish  | 把 1px 直线换成极淡曲线或带小图标的断线    | **成本极低但精致感回报最高**，因分隔线数量多、出现频繁       |
| **等待态意象** waiting motif | 唯一允许有动画的花纹                       | 见 7.4                                                       |

### 7.3 意象取材与搭配

筛选标准只有一条：**能否用 3 条以内的路径画出来，且缩到 12px 还认得出。**
认不出的就不是图案，是噪点。

**入选**：

| 意象         | 出处                | 扁平化形态                                          |
| :----------- | :------------------ | :-------------------------------------------------- |
| **咖啡豆**   | Rabbit House 咖啡厅 | 椭圆 + 中间一道曲线，几何上极稳                     |
| **兔耳**     | usa 的核心          | 两枚圆角长叶形，全套辨识度最高                      |
| **杯碟俯视** | 咖啡厅日常          | 同心圆 + 一段弧（把手），同心圆正好呼应同心圆角规则 |
| **热气曲线** | 咖啡杯上的蒸汽      | 两三道 S 形，天生适合分隔纹与动画                   |
| **风的流线** | kaze                | 长短不一的圆头细线，与热气同族但更舒展              |
| **方糖**     | 咖啡配件            | 圆角方块，可当微平铺里的「小点」                    |

**落选**：拉花兔（细节太多，缩小即糊）、具体角色元素（太指向个人）、
写实兔子轮廓（曲线多，扁平化后易像别的动物）。

**定案搭配**：

```
微平铺    咖啡豆 + 方糖      最中性，可大面积铺
角落纹样  兔耳               辨识度担当，全程只在少数几处露面
分隔纹    热气 / 风流线
```

兔耳作为最抢眼的意象刻意稀缺：**稀有才显得是彩蛋，铺满就成了装饰壁纸。**

### 7.4 技术机制：一份资产吃两套主题

**不为深浅主题各画一套 SVG。** 用 `mask-image` 让颜色由 CSS 变量给：

```css
.ornament {
  position: absolute;
  inset: 0;
  pointer-events: none; /* 必须，否则挡住点击 */
  background-color: var(--pattern-ink);
  mask-image: url("@/assets/patterns/beans.svg");
  mask-size: 56px;
  opacity: var(--pattern-alpha);
}
```

SVG 只描述**形**，颜色与浓度全在令牌里。换主题、调浓淡、日后做别的配色都不用
碰资产文件——**双主题不会走样，因为它们本来就是同一个文件。**

```css
/* 深色 */
--pattern-ink: var(--color-accent);
--pattern-alpha: 0.035;

/* 浅色 */
--pattern-ink: var(--color-text);
--pattern-alpha: 0.05;
```

深浅取的**不是**同一种墨色：深色底上用主色粉调会透出一层很淡的暖意；
浅色底上主色粉会发脏，改用文字色更干净。浓度也不同——浅色底对低对比更不敏感，
需稍提一点才看得见。这与第 4.2 节「浅色主题不能只换变量」是同一个道理。

**资产用独立 `.svg` 文件而非内联 data-URI**：桌面应用读本地文件几乎无成本，
而独立文件可被 Vite 指纹缓存，改图时 diff 也看得清。

**禁止**在花纹中使用 SVG `filter`、`blur`、渐变网格——这些会让合成器逐帧重算，
在长列表上直接掉帧。**花纹是纯静态的填色形状，一步都不能多。**

### 7.5 浓度天花板

```
微平铺      2% ~ 4%
角落纹样    3% ~ 6%
分隔纹      6% ~ 10%（线本身就该看得见）
绝对上限    8%（分隔纹除外）
```

**判定标准**：

> **把界面截图缩到 25%，如果还能明确看出「这里有花纹」，就是太浓了。**

正确的浓度是——盯着看能看到，扫过去只觉得这块地方「不空」。

**对比度纪律**：花纹的明度差必须小于底色的 2%，这样正文对比度仍可按纯底色
计算，无障碍结论不会因装饰而失效。超过就得逐处重算对比度，**那是维护噩梦**。

### 7.6 只有等待态允许动

装饰一旦自己动起来就变成「为炫技而动」，违反「不喧宾夺主」。故：

> **静态花纹永不动画。唯一例外是等待态意象。**

具体做法：试下载期间，一只杯子的热气缓缓上升循环
（`transform: translateY` + `opacity`，两个合成器属性，零重排）。
等待结束立刻停住并淡出。

**不做「完成庆祝动画」** ——用户此刻要看的是结果，不是表演。

这落在铁律二的「等待中」时刻，并与 5.5 节逐条出结果配合。

### 7.7 品牌标识位

**顶栏当前使用 emoji `🐰`，需替换。**

它与原生控件是同一类问题：**由系统字体渲染，每台机器长得不一样，而且是彩色的**
——一个饱和度爆表的彩色 emoji 坐在克制的冷紫界面里，会成为全屏最抢眼的东西，
**而它并不承载信息**。

该槽位定性为**品牌标识位**（不是装饰位）：

- 标识是身份，装饰是氛围，**两者不混**
- 先放一枚遵循统一图形词汇的**占位 SVG**，真正的 LOGO 日后直接替换文件

**统一图形词汇**（标识与全部花纹共用）：

```
栅格 24px · 线宽 1.5px · 端点圆头 · 最小圆角 2px · 不出现尖角
```

统一图形词汇是「装饰看起来是长在界面上，而不是贴上去」的技术原因。

## 8. 术语帮助与文案

### 8.1 术语帮助系统

本工具的术语密度客观上极高且**绕不开**：清单包、DLC、depot、manifest、GID、
lua、AppID、注入器、源、额度、认证源、仅本体……

这些不是「换个说法就懂」的词，它们是**领域事实**，改写只会造成更大误解。

故只有一条路：**词照原样用，旁边给出口。**

> **信息不删，只折叠。默认给结论，展开给细节。
> 删信息是照顾小白，藏信息才是同时照顾两边。**

#### 三级机制

| 级别   | 形态                                           | 用途                                 |
| :----- | :--------------------------------------------- | :----------------------------------- |
| **L1** | 术语后紧跟 `?` 徽章，悬停 / 键盘聚焦出 Tooltip | 一句话说清「这是什么」，硬性两行以内 |
| **L2** | Tooltip 内「了解更多」，**就地内联展开**段落   | 说清「为什么你会遇到它」             |
| **L3** | 折叠区块                                       | 原始 GID、路径、日志片段等完整数据   |

L1 必须能独立成立——它是绝大多数人唯一会用到的一级。

L2 选择就地内联而非跳转统一术语页：**用户在对比表看到「仅本体」时想知道的是
这一行的事，跳走会丢上下文。** 内联展开会撑开列表、导致行位置跳动，
以第 5 章的过渡动效缓解。

#### 三条硬约束

**① 悬浮提示里不能放唯一一份关键信息。**
触屏没有 hover、读屏用户拿不到、截图截不到。凡是「不看就会做错」的内容必须写在
正文里，`?` 只放补充。

**② 必须是真正的 `<button>`。**
能 Tab 聚焦、聚焦即显示、Esc 可关。挂在 `<span>` 上的 tooltip
**等于对键盘用户不存在**。

**③ Tooltip 必须可被点击固定。** 悬停即消失的提示对阅读长句是灾难。

**④ `?` 不能到处都是。** 判定标准：
**只在「不懂这个词就没法做决定」的地方放。**
对比表里的「仅本体」要放（它决定用户换不换源）；hero 区的发行日期不放。
一屏超过三四个 `?` 就该反思是不是正文没写好。

#### 优先级最高的六处

1. 对比表的 **「仅本体」/「不可用」/「需要额度」** —— 直接决定用户下一步动作
2. **「源」** 本身 —— 用户根本不知道清单从哪来
3. **API 额度 / 凭据到期** —— 涉及要不要去申请、为什么会失效
4. **「注入器 / OST」** —— 三层解耦的关键，用户搞不清盒子与 OST 的分工时会问
   「为什么装了没生效」
5. **「清单包」与「本地导入」** —— 本地导入是一等入口，但名字完全不自解释
6. **DLC 勾选的自动落盘** —— 「不用点保存」违反直觉，需要一句解释

#### 架构位置：术语表须有单一事实来源

**前端一个 `glossary.ts`，不走后端。**

```ts
key -> { term, short, long? }
```

三条理由：

- 它是纯展示文案，**跨 Wails 边界毫无收益**，还会多出一个 DTO 要维护、
  多一次 `wails generate module`
- **同一术语在多处出现必须字字相同。** 散写在各 `.vue` 里，改一处漏三处几乎
  必然发生，而**同一个词在不同页面解释得不一样，比不解释更伤信任**
- **教程文档可共用同一份措辞。** 界面与教程一致，用户在两处之间不会迷路——
  这对封测阶段的答疑成本是实打实的削减

### 8.2 文案语气

**情绪价值必须挂在事实上。** 每步都撒花会让用户觉得被当小孩哄。

> **鼓励只在用户真的完成了一件事时出现，且必须同时给出事实。**

「装好啦，64 个 DLC 都到位了」远胜「太棒了！！」——前者**既有情绪也有信息，
用户能验证**。

**失败时最需要的鼓励是「这不是你的错」。**
所有源都给 0 个 DLC 时，明确说「是社区还没收录，不是你操作错了」，
比任何颜文字都更能安抚人。项目现有文案已在这么做，需系统化延续。

**语气分区**（避免 PCL2 第 2.4 节那个坑）：

> **正文端正，反馈时刻放松。**

- 错误提示、说明文字、术语解释：**保持冷静专业**——此处任何俏皮都会显得不负责
- 成功提示、空状态、劝退文案：允许人味

### 8.3 两句名场面文案的落点

#### 「如果你不知道这是干嘛的，最好别动它」

**落点**：设置页的「调试」小节，以及 PROGRESS 第 4 号议题（自定义源）落地后的
源编辑区——那里用户要填 URL、选源类型，**填错了不报错但拿不到清单**，
正是最该劝退的地方。

现有的 Steam 路径手填、源启用开关也属于「改错了会坏」的范畴。

**配套视觉规则**：

> **高级区不隐藏，但要「视觉下沉」。**

用更低的对比度、更小的字号、默认折叠，明确传达「这里不是给你准备的」。
**藏起来会让老手找不到，完全平铺会让小白误触，下沉是唯一同时照顾两边的做法。**

**语气注意**：这句话的杀伤力在于**它是善意的**，不是嘲讽。故更接近
「这些是给知道自己在做什么的人准备的，不确定就别改，默认值对绝大多数人都是
对的」——**必须给出「不动也没问题」的保证**。小白最怕的是「不动是不是也错了」。

#### 「请把报告文件发给对方，而不是发这个窗口的照片或者截图」

**立刻可用**——上一轮已完工并实机验证的 `ExportDiagnostics`（脱敏诊断包）
正是它的落点。

价值远超字数：封测阶段最大的时间黑洞就是**用户发一张糊掉的截图，然后来回问
五轮才拿到真正需要的信息**——而截图里通常恰好没有日志、没有版本号、
没有环境检测结果，**这三样全在诊断包里**。

做成一组，不是单句：

| 位置                 | 内容                                                                                          |
| :------------------- | :-------------------------------------------------------------------------------------------- |
| **导出按钮旁**       | 常驻这句提示，且说明包里有什么、**已经脱敏了**（打消隐私顾虑，否则用户不敢发）                |
| **导出成功后**       | 「已保存到 xxx」+「群里报障时把这个文件拖进聊天窗口就行」——**给具体动作，不只是告知有个文件** |
| **任何错误提示末尾** | 附「导出诊断包」入口。**报错当场是用户最愿意配合的时刻**，隔一步他就懒了                      |

**与 QQ 群规对齐**：群规里已写好报障格式模板，
**群规要求什么，界面就直接产出什么**——两边对齐了用户才不会觉得报障麻烦。

## 9. 设置项纪律（与 PCL2 反向）

PCL2 设置项极多，因为它的用户就是来折腾的。风兔盒处境相反：
**它的价值在于把复杂性吃掉**——三条铁律里两条就是「我们不让用户面对这些」。

> **设置项越多，越是在把复杂度还给用户。**

故方向定为**少而准**。新增任何设置项须回答：
**不加这一项，用户是否会卡住？** 答不出就不加。

### 但自定义源入口应当做

它性质不同：**不是增加复杂度，而是把「等下一个版本」这个无解的等待变成可解的
动作**——减少的是无力感。

背景（见 PROGRESS「源生态维护是核心长期任务」）：源列表当前硬编码在
`defaultRepoSources()`，发现一个好源要等下一个版本才能给用户用。

**这与堆设置项是两回事。** 落在「清单源」小节，配合 8.3 节的劝退文案。

## 10. 试下载对比表的状态呈现

### 10.1 现有 `border-left` 方案作废

问题不是配色，而是**几何打架**：3px 直角色条贴在 12px 圆角卡片左侧，
色条上下两端是方的、卡片角是圆的——于是色条看起来像「贴上去的胶带」，
而不是卡片自己「长出来的」。

**怎么调色都救不回来。**

### 10.2 改为双重编码

书脊思路（不占宽度、形成纵向印象）保留，改为：

**① 数字自己承担状态。**
DLC 数放大加粗，颜色即状态。依据：对比表的核心动作是纵向扫一列数字，
状态长在数字上，**一眼同时得到「多少」和「行不行」，比左边框省一次眼动**。

**② 整行极淡染色。**
状态色以 4~6% 透明度铺整行背景。单看比色条弱，但覆盖面大，
形成整体印象反而更强。

两者都不占横向宽度，叠加使用。

### 10.3 五种状态仍须各自可辨

| 状态                   | 含义     | 编码                           |
| :--------------------- | :------- | :----------------------------- |
| `ok`                   | 可用     | 状态色-可用 + 数字强调         |
| `empty`                | 仅本体   | 状态色-警示                    |
| `unsupported` / `miss` | 不可用   | 状态色-中性 + 降透明度         |
| `failed`               | 网络失败 | 状态色-危险                    |
| `skipped`              | 未试取   | **虚线描边**，表达「还没发生」 |

`unsupported` 与 `miss` 同色处理：对用户而言两者处置方式相同（换源），
无需在视觉上再作区分。此项继承既有实现。

## 11. 前端架构（技术向）

### 11.1 一条主线：单向依赖

现有目录（`views / components / stores / composables / api`）本身没问题，
问题是**分层没有依赖方向**——任何组件都能 import 任何东西。

等自绘控件一多，就会出现「一个复选框里塞了 store 调用」这类事，
之后想复用就搬不动了。

故整套架构只有一条铁律：

> **`ui/` 是纯的：不得 import stores、api、wailsjs、router。**

```
wailsjs（生成物）
   ^
 api/  ------------+
   ^               |
stores/         composables/
   ^               ^
   +---- domain/ --+        <- 业务组件，可用一切
              ^
            ui/               <- 纯表现，只吃 props、只吐 emits
              ^
          layout/ views/
```

**判定方式**：`ui/` 下任一组件，复制到另一个项目就能跑。做不到就说明漏了依赖。

**配套边界**：只有 `api/` 与 `useWindowControls` 可以 import `wailsjs/`。
这条现状已守着，写下来是防以后。

### 11.2 目录结构

### 11.3 CSS 分层：用 `@layer` 免掉特异性战争

自绘控件会带来一个必然矛盾：原语自己有一套样式，业务侧又想微调
（如 `TrialRow` 里的按钮要 `white-space: nowrap`）。不管这事，
迟早出现 `!important`。

```css
@layer tokens, base, ui, domain, utilities;
```

**后声明的层永远赢，与选择器权重无关。** 于是业务侧一个普通类名就能覆盖原语
样式，不必比谁的选择器长。`utilities` 放最后，让 `.u-truncate` 这种总是生效。

**scoped 与全局的分工**：

- 原语自己的样式写在组件内 scoped（跟着组件走）
- 只有令牌、reset、花纹、utilities 进全局

**既有全局 `.btn` 转为过渡期 shim**：标注废弃、行为不变，等所有调用点换成
`<UiButton>` 后删掉。**不搞一次性全替**，那样 diff 大到没法 review。

顺手修一个实际缺陷：`.btn` 漏了 `font-family: inherit`，
Windows 上按钮会掉回系统 UI 字体、与正文不同源。`UiButton` 中补上。

### 11.4 路由：嵌套是侧栏常驻的技术前提

```
/setup                        -> SetupView（独立全屏）

/                             -> HomeShell      侧栏：入口 + 品牌 + 状态摘要
   ├─ ''        (search)      -> SearchPane
   ├─ 'import'                -> ImportPane
   └─ 'app/:appID'            -> GamePane

/library                      -> LibraryShell   侧栏：已安装游戏列表
   ├─ ''                      -> LibraryOverviewPane
   └─ ':appID'                -> GamePane

/settings                     -> SettingsShell  侧栏：四个小节
   └─ ':section'              -> 对应 Pane

/game/:appID                  -> 重定向至 /app/:appID（旧路径兼容）
```

**第 3 步的实际落地与上表有一处差异**：`/settings` 下暂时只有 `''` 一条
子路由指向未拆的 `SettingsView`，侧栏用 `scrollIntoView` 锚点跳转过渡。
`:section` 子路由归第 4 步——627 行的拆分与路由改造混进同一个 commit，
回退时就分不开了，而第 3 步是六步里唯一有回退风险的一步。

换子路由时只需把 `SidebarItem` 的 `@click` 换成 `to`，侧栏结构一行不动。
**这是刻意留的接缝。** 过渡期代价：地址栏不变，刷新回不到刚才那一节。

`/game/:appID` 保留重定向而非直接删除：它在 07-29 前是正式路径，
改造前若有调用点遗漏，重定向能让它继续工作而不是白屏。

关键在于：**`:appID` 变化时父级 Shell 不重建。** Vue Router 的嵌套路由天然
如此，所以侧栏保持不动、列表滚动位置不丢、选中态指示器可以平滑滑移——
**第 5.2 节那个动效不需要任何额外机制就成立了。**

#### 一个必须写死的坑

> **不要给 `<RouterView>` 加 `:key`。**
>
> **以及任何与之等价的东西**——包括 `:key="route.path"` 与
> `:key="route.fullPath"`。

加了 key 会强制重建组件，那么 `GameView` 里现有的 `watch(appID, load)`
**永远不触发**——而那段逻辑是实机验证过的。不加 key 则组件实例复用、
watch 正常工作，改动量最小。

⚠️ **实测补充（2026-08-01，第 3 步）**：本条原先只写了 `:key="appID"`，
施工时的第一版 `PaneTransition` 因此改用了 `:key="route.path"`——
**那是等价的**，`:appID` 变化时 `path` 也变，同样销毁重建。
已在 `PaneTransition.vue` 内以注释写死，此处补全约束范围。

**推广到一条一般判断**：凡以「不要用 X」形式写下的约束，都应补一句
「以及任何与 X 等价的东西」，否则读者会绕道踩进同一个坑，
而且会觉得自己已经遵守了规则。

不加 key 的实际行为（已确认）：

- 切到不同组件（`SearchView` → `ImportPane`）：vnode 类型不同，
  `Transition` 正常播放
- 同组件换 `appID`：实例复用、无过渡、watch 触发、内容就地更新。
  **这正是 5.2 节要的效果**——侧栏指示器滑移，右侧就地换内容，
  而不是整块闪一下

写进本文是为了防止以后有人「为了保险」加个 key，**静默改掉已验证的行为**。

#### 过渡必须挂在滚动容器内部

`PaneTransition` 自带 `ContentPane`（滚动容器），并把 `Transition` 包在其内。

反过来把过渡挂在滚动容器外面，切换瞬间滚动容器本身参与位移，
滚动条会跟着抖一下——**那是「界面是拼出来的」那种观感的典型来源**，
且用户说不出哪里怪。

顺带一并收进 `ContentPane` 的还有限宽与留白。现状 `SearchView` 与 `GameView`
各写一份 `max-width: 860px; margin: 0 auto`，那种「每页自己记得对齐」的做法
迟早对不齐。`SettingsView` 是刻意的例外（760px，长文本行宽），
已在该文件内注明「不是漏改」。

#### `keep-alive` 边界

- **只包 `SearchPane`** —— 搜索结果值得留
- **不包 `GamePane`** —— 它的状态量大（试下载报告、勾选、同步状态），
  缓存起来的失效判断比重新加载复杂得多。而后端试下载缓存 TTL 30 分钟，
  重进几乎零等待——**代价已经在后端付过了，前端不必再付一次**

### 11.5 自绘原语的统一契约

八九个控件若各写各的 API，用起来会比原生更痛。统一为：

```ts
// 所有值型控件
modelValue + @update:modelValue   // 支持 v-model
disabled?: boolean
size?: 'sm' | 'md'                // 只两档，不做 lg
invalid?: boolean                 // 校验态，视觉由原语自己管
```

实现要求见第 6.3 节三条。

#### 契约类型必须住在 `.ts` 里，不能写在 `.vue` 中

`<script setup>` 里的 `export interface` **无法被别处再导出**，`vue-tsc` 报
TS2459。故 `SelectOption` / `SegmentedOption` 这类调用方需要引用的类型
统一放 `ui/types.ts`。

这个限制反而指向更好的结构——**契约与实现分离**：调用方只需 import 类型
即可构造数据，不必知道是哪个组件在消费它。

### 11.6 动效的工程化：三个机制，不是散写

**① `PaneTransition`**
包住内容区的 `<RouterView>`，把第 5.1 / 5.2 节的时长与曲线固化成组件。
**页面自己不写任何 transition 类。**

**② `useStagger`**

```ts
const { styleFor } = useStagger({ max: 8, step: 24 });
// styleFor(i) -> { '--stagger-i': Math.min(i, 8) }
```

延迟在 CSS 里算（`animation-delay: calc(var(--stagger-i) * var(--stagger))`），
**JS 只发序号不碰时间**。

上限 8 硬编码在 composable 里，防止有人在 200 行列表上开错开——
那会让最后一行等 4.8 秒，**动效直接变卡顿**。

**③ 可中断性靠 CSS transition 天然获得**

> **位置 / 透明度过渡一律用 `transition`，只有循环动画（热气）用 `animation`。**

`animation` 不可中断，一旦用在交互过渡上就违反第 5.4 节第二条。
这是个很容易踩的坑，值得写死。

### 11.7 状态归属

| 状态                     | 放哪                           | 为什么                           |
| :----------------------- | :----------------------------- | :------------------------------- |
| env / config / library   | 现有 stores，不动              | 已验证                           |
| 侧栏折叠、当前 banner    | `ui` store                     | 跨页存活                         |
| 搜索关键词与结果         | `SearchPane` 局部 + keep-alive | 只有它自己关心                   |
| 试下载报告、勾选、同步态 | `GamePane` 局部                | 生命周期与该游戏绑定             |
| 库概览统计               | `library` store 的 computed    | 侧栏与概览页都要读，派生而非另存 |

**试下载报告刻意不提到 store。** 提上去唯一的好处是侧栏能显示徽章，
代价是要处理「切游戏时清哪些、留哪些」——**而这类跨组件生命周期的清理逻辑，
正是最容易漏出 bug 的地方**。等真需要侧栏徽章时再提，不预先设计。

### 12.2 第 1 步的完成判据

「界面变色但功能不变」偏软，补三条可验真的：

1. `styles/tokens/` 下**不出现任何选择器**，只允许 `:root` 与
   `:root[data-theme="..."]`。出现别的说明有样式混进了令牌层。
2. 全局 CSS 中搜不到 `#ffffff` 与 `#000000`（第 4.1 节双主题均不含纯白纯黑）。
   `rgba(255,255,255,...)` 用于内高光是允许的，那是光不是色。
3. 层顺序声明落入构建产物。判定方式：`findstr domain dist\index.html`
   须有输出——`domain` 一词只出现在顺序声明里，是最好的探针。

#### ⚠️ 实测：层顺序声明不能写在 CSS 里（2026-08-01）

**Vite 的 `@import` 内联流程会把不含任何规则的裸 `@layer` 声明整条抹掉。**
写在 `styles/index.css` 顶部、或单独成 `layers.css` 再 `@import`，
两种写法都一样被吃掉——产物中 `domain` 一词完全消失。

后果：层顺序退化为「首次出现顺序」。而 `domain` 层在第 1 步没有任何文件，
于是它**根本没被注册**；第 4 步业务组件开始用它时，覆盖关系会全乱。

**这个失效完全静默**：不报错、不警告，`vite build` 一样成功，
产物哈希甚至一字未变——正是这一点让它极难被发现。

**定案写法**：顺序声明放在 `frontend/index.html` 的内联 `<style>` 里。

```html
<style>
  @layer tokens, base, ui, domain, utilities;
</style>
```

可行的原因：这条不经 PostCSS，Vite 不会改它；而 CSS 规范规定层顺序由
**首次出现**确定，内联样式表先于外链 CSS 解析，故此处必定是第一次出现。

代价是层结构改动时要同步两个地方（`index.html` 与 `styles/index.css` 的
`@import` 分组），两边都写了交叉引用注释。

**推广到一条一般判断**：凡是「只声明不产生规则」的 CSS at-rule，
都要假设构建工具可能把它当空语句优化掉，**必须验产物而不是验源码**。

#### 补注：同一形状的无害版本（2026-08-01，第 4 步验产物时发现）

产物里还有一条裸声明 `@layer base;`，来源是 `base/frameless.css`——
该文件**只有注释、没有任何规则**（frameless 的实际样式随 TopBar 走，
文件本身是约束的存放处）。Vite 同样把它压成了裸声明。

**这一条无害**，因为 `base` 层已由 `reset.css` / `scrollbar.css` /
`a11y.css` 三个有规则的文件注册过了，这条裸声明是空操作。

由此把判据说得更准一点：**危险的不是「出现裸声明」，而是「某一层的全部
文件都不产生规则」**。第 1 步 `domain` 出事正是因为它当时一个文件都没有；
而它在第 4 步有了 `domain/settings.css` 之后，这个风险自然消失。

推论：**新增一个空层时最危险**。若某层暂时没有内容，要么先不声明它，
要么放一份带真实规则的文件进去，别让它以「已声明」的假象存在。

#### ⚠️ 实测：`check-tokens` 曾对本步的关键状态是瞎的（2026-08-01）

摘除 `legacy.css` 的 `@import` 之后，`check-tokens` 报告的已定义令牌数
**一个没少**（仍是 72）。原因是它按**目录**收集定义（`walk(TOKEN_DIR)`），
不看文件是否真的被 `index.css` 引入。

于是存在这样一个状态——**`legacy.css` 在浏览器里已完全失效，但脚本仍把它
定义的 13 个旧令牌算作「已定义」，任何遗漏引用都被放过。**
而这个状态正是「删除 legacy.css」的前一步，也就是最需要检查的那一刻。

**已修**：改为只收集被 `index.css` 实际 `@import` 的令牌文件，
并对「磁盘上存在但未被引入」的令牌文件**直接报错**——那是最危险的形态，
它看起来还在项目里，但对浏览器不存在。要么引入，要么删掉，不许以此状态留存。

**由此得到一条一般判断**：**判据本身也要有判据。**
凡是「扫目录得出结论」的检查，都要问一句「目录里的东西是否等于实际生效的
东西」——在有构建步骤的项目里，这两者默认不相等。

这与第 1 步 `@layer` 被吃掉、以及本节账本误判 `--color-success` 无调用点，
是同一类问题的三次不同表现：**检查手段自身的失效是静默的。**

⚠️ 新增文件不得再引用旧令牌名。别名是给既有调用点的过渡期通道，
新代码走它只会让 `legacy.css` 更难删。第 3 步新建的 8 个文件已全部直接用新名。

## 14. 性能纪律（继承并强化）

沿用既有三条，新增两条：

1. **只过渡 `transform` 与 `opacity`。** 侧栏高度过渡是**唯一**允许的例外——
   它是三板斧动效的一部分，且只在跨页切换时发生一次。
2. **长列表容器 `content-visibility: auto`。** 侧栏游戏列表尤其需要。
3. **`will-change` 仅在动画期间保留。** 长期挂着白占显存。
4. 🆕 **花纹不得使用 `filter` / `blur` / 渐变网格**（第 7.4 节）。
5. 🆕 **错开入场最多 8 项**（第 5.1 / 11.6 节）。

## 15. 无障碍（继承并强化）

1. 尊重 `prefers-reduced-motion`，且**必须真正禁用位移类动效**，
   不只是缩短时长（第 5.6 节）。
2. 焦点环全局可见；**自绘控件必须自行实现 `:focus-visible`** ——
   这是自绘的主要代价，不得省略。
3. 可点区域不小于 28×28px。
4. `?` 徽章必须是真 `<button>`，且 `aria-describedby` 关联提示内容。
5. 悬浮提示中不得放唯一一份关键信息。
6. 装饰花纹明度差小于底色 2%，使正文对比度可按纯底色计算。
