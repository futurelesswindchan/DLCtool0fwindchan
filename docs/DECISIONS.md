## 2026-07-07: 项目定位为"MOD 盒子管理器"，与底层工具完全解耦

**背景**：v1.4 硬耦合 SteamTools（直接写 config.vdf + Steamtools.lua + 复制 manifest），导致底层工具停更时整个工具链断裂。

**结论**：

- 盒子不写 config.vdf
- 盒子不写注入器自身的配置文件
- 盒子只负责把 Lua 清单文件放到注入器的监控目录
- 注入器环境仅做"检测 + 状态提示"，不帮安装不帮修复（方案 A）
- 用户通过博客上的教程自行安装注入器

**背景**：SteamTools 自 2026.01 起停更半年，与 V 社夏促后的新版 Steam 客户端冲突，导致 Steam 崩溃重启、游戏闪退。也许已经遗憾离场awa。

- 适配对象为 OpenSteamTool（活跃维护的开源替代品）
- 旧用户自行卸载 ST + 清理残留（有教程指引）

## 2026-07-07: 使用 JSON 文件做持久化，不引入 SQLite

**背景**：SQLite 引入 CGO 依赖，会让 Wails 交叉编译变复杂；本项目数据量小（配置 + 几十条历史记录）。

**结论**：

- 用户配置：`~/.kazeusa/config.json`
- 安装历史：`~/.kazeusa/history.json`
- 写入策略：先写 .tmp 再 rename（原子写入）
- 零外部依赖，保持打包清爽

## 2026-07-07: 每游戏一个独立 Lua 文件

**背景**：OST 支持 `config/lua/` 目录下多文件热重载。相比 ST 的单文件追加，独立文件便于管理和清理。

**结论**：

- 每个游戏生成独立文件，命名格式：`<GameName>_<MainAppID>.lua`
- 安装 = 放文件，卸载 = 删文件
- 干净利落，不影响其他游戏

## 2026-07-08: 部署策略——推荐 tmp+rename 原子写入

**背景**：OST 的 LuaFileWatcher 使用 ReadDirectoryChangesW 事件驱动 + 500ms 防抖窗口。如果先创建空文件再写内容，可能被中途触发解析。

**结论**：

- deployer_ost.go 写入 .lua 时，先写 `<filename>.tmp` 再 `os.Rename` 为 `.lua`
- 这样 OST 只收到一次 RenamedNewName 事件，拿到完整内容
- 不需要加锁、不需要通知 OST、不需要等待确认

## 2026-07-08: OST 环境检测方案确定

**背景**：通过 OST 源码确认了加载链：dwmapi.dll / xinput1_4.dll 作为 DLL 劫持入口，加载 OpenSteamTool.dll。

**结论**：

- detector_ost.go 检测逻辑：在 Steam 根目录检查以下三个文件是否存在
  - `dwmapi.dll`（入口代理 A）
  - `xinput1_4.dll`（入口代理 B）
  - `OpenSteamTool.dll`（核心 DLL）
- 三者全部存在 → Available
- 缺少任一 → Not Available，Message 提示缺少哪个文件
- 不检测版本、不检测 pattern 缓存、不检测 toml 配置（那些是 OST 自己的事）

## 2026-07-26: 模块间用接口解耦，不自建事件总线

**背景**：考虑引入事件总线做模块间松耦合通信。

**结论**：不引入。后端仅 6 个模块，调用关系是一条无环无交叉的直线，事件总线的收益不足以抵偿代价——可追溯性归零（无法通过 IDE 跳转找到调用方）、类型安全丧失（`any` + 断言把编译期检查推迟到运行时）、错误传播需另造回执机制。

- 模块间解耦交由 `Deployer` / `Detector` 接口承担，这已是恰当的粒度
- **唯一使用事件的场景是跨进程边界**：Go → Vue 的单向进度通知，直接用 Wails 内置的 `runtime.EventsEmit`，不自造第三套总线
- 判据：模块数量增长到出现环形依赖时再重新评估

## 2026-07-26: 多源回退用 slice 顺序遍历实现，暂不引入策略模式

**背景**：考虑用责任链模式 + 策略模式组合来组织资源管理。

**结论**：责任链的**精神**采用，**样板代码**不采用；策略模式暂缓。

- `repo_client.go` 的多源回退用 `for range sources` + 首个成功者返回实现，约十行，不需要 `setNext()` 链表结构与 interface 层级
- 策略模式暂不引入：当前每个操作都只有一种合法算法（解析只有 Lua VM、部署只有 tmp+rename、检测只有查三个 DLL），找不到「多算法可互换」的落点。过早抽象比重复代码更贵
- `Deployer` / `Detector` 接口本质上已是策略模式（OST 是一种实现，未来其他注入器是另一种），无需再叠一层

## 2026-07-26: 在线仓库采用分层缓存，健康度探测改为手动触发

**背景**：v2.0 的多源下载需要决定「智能」到什么程度。

**结论**：分三层，其中两层必做、一层延后且改为手动。

| 层级          | 内容                                               | 时机                                          |
| :------------ | :------------------------------------------------- | :-------------------------------------------- |
| L1 顺序回退   | 按源列表逐个尝试，失败换下一个                     | v2.0-beta 必做                                |
| L2 健康度探测 | 并发测速后按延迟排序                               | v2.0-rc，且**由用户点击「测速」按钮手动触发** |
| L3 本地缓存   | 索引缓存 1 小时过期；清单包永久缓存 + 提供清空按钮 | v2.0-beta 必做                                |

L2 不做自动后台探测的理由：启动时并发请求全部源，在防火墙或网络受限环境下会让用户看到一片失败标记，制造无谓的焦虑。

仓库源支持内置默认 + 用户自定义，可增删改与「重置为默认」，配置载体为 `config.json` 的 `repoSources` 字段。

## 2026-07-26: 前端不引入 UI 组件库，纯 CSS 优先

**背景**：Wails 受 WebView2 约束，无法像 WPF 那样做重度定制渲染，故希望尽量用 CSS 承担表现层。

**结论**：采纳纯 CSS 优先，并明确三条性能纪律。

- **不引入 UI 组件库**（Element Plus / Naive UI 等）：本工具 UI 高度定制（卡片 / 拖拽区 / 列表），可复用的仅按钮与弹窗，而组件库会把 `frontend/dist` 从 ~100KB 推到 1MB+
- **DLC 列表用 `content-visibility: auto`** 让浏览器跳过屏幕外元素渲染，一行 CSS 替代整个虚拟滚动库
- **动画只改 `transform` 与 `opacity`**，二者走 GPU 合成层；禁止对 `width` / `height` / `top` 做过渡（触发重排）
- 主题切换走 CSS 变量 + `:root[data-theme]`，切换时只改一个 attribute，不引发 Vue 重渲染

补充认知修正：渲染瓶颈并非「WebView2 弱于 WPF」——其底层即 Chromium，CSS 动画性能良好；真正的风险点是 Vue 响应式开销与重排重绘。

## 2026-07-26: 全部落盘文件收拢至 ~/.kazeusa/，统一命名为 kazeusa

**背景**：v1.4 未设置 `WebviewUserDataPath`，WebView2 遂在 `%APPDATA%\<exe文件名>\` 下自建目录（连 `.exe` 后缀一并带上）。exe 改名后旧目录永久残留且无人清理，实测已产生 `DLC入库工具.exe` 与 `DLC入库工具v1.4.exe` 两坨垃圾。同时排查出日志写在 `%TEMP%`（会被系统清理抹掉，用户报障时无线索）、日志无轮转、`Logger.Close()` 从未被调用、临时解压目录无兜底清理等一系列问题。

**结论**：

命名统一（exe 名务必纯 ASCII，中文 exe 名会让 WebView2 目录与崩溃转储路径都带上中文）：

| 项目              | 取值                                         |
| :---------------- | :------------------------------------------- |
| go module         | `dlctool`（保持不变，改动需重写全部 import） |
| exe 文件名        | `kazeusa.exe`                                |
| 窗口标题 / 显示名 | `风兔盒 - 请问您今天要来点DLC吗？`           |
| 数据目录          | `~/.kazeusa/`                                |

允许的落盘位置**穷举如下**，此外一律禁止：

```plain
%USERPROFILE%\.kazeusa\
├── config.json          用户配置
├── history.json         安装历史
├── logs\                日志（5MB × 3 份轮转）
├── cache\               仓库索引与清单包缓存
└── webview2\            WebView2 运行时数据（本次收拢）

<Steam>\config\lua\<游戏名>_<AppID>.lua    唯一的外部写入
%TEMP%\dlctool_*\                          解压临时目录，用完即删
```

配套修改：

- `main.go` 显式设置 `WebviewUserDataPath` 指向 `~/.kazeusa/webview2/`
- `main.go` 补 `OnShutdown` 回调——此前完全缺失，是结构性缺口。日志 flush、未来的下载协程与缓存写入都需要这个退出钩子
- `logger.go` 日志迁至 `~/.kazeusa/logs/`，实现 5MB × 3 份轮转
- `app.go` 的 `startup` 中兜底清理 `%TEMP%` 下超过 24 小时的 `dlctool_*` 残留（设时间门槛以免误删另一实例正在使用的目录）
- `wails.json` 与 `main.go` 的窗口尺寸、背景色对齐（此前 json 写 `#ffffff` 而 main.go 写深灰，会闪白屏；json 中的 `maxWidth/maxHeight` 属死配置，改之无效）
- **不自动删除 v1.4 的 AppData 残留**：删除他人 `AppData` 目录需判断「是否为我所建」，判断失误即误删用户数据，此行为本身就不优雅。改由博客迁移教程指引用户手动清理

**验收标准**：卸载 = 删 exe + 删 `~/.kazeusa/` 一个文件夹。

## 2026-07-27: Steam 路径的唯一权威是 config.json，Deployer 改路径后重建

**背景**：v1.4 在 `App.steamPath` 字段与配置中各存一份 Steam 路径，导致用户在设置中改了路径后，部分操作仍使用旧值——这类双源真相引发的不一致极难排查。

同时，`Deployer` 在构造时固定 `steamPath`，需决定路径变更后如何处理。

**结论**：

- **移除 `App.steamPath` 字段**。唯一权威是 `config.json`，需要时经 `a.steamPath()` 读取，且明确约定不缓存返回值
- **Deployer 采用重建而非原地修改**（候选方案见下表）。改 Steam 路径是极低频操作，多数用户一生只做一次，为它污染接口签名不值得

| 方案      | 做法                                                      | 取舍                                                       |
| :-------- | :-------------------------------------------------------- | :--------------------------------------------------------- |
| A（采纳） | 路径变更时 `a.deployer = NewOSTDeployer(newPath, logger)` | 部署器内部无可变状态，也就无竞态；代价是调用方必须记得重建 |
| B         | 接口改为 `Deploy(steamPath, gp, ids)`                     | 无状态，但每个方法签名都要多带一个参数                     |

- 为防止「改了路径忘记重建」，将写配置与重建部署器打包为 `persistSteamPath`，`GetSteamPath` 与 `SetSteamPath` 均经由它执行。新增改路径入口时应沿用此函数

## 2026-07-27: GameRecord.InstalledAt 使用 RFC 3339 字符串而非 time.Time

**背景**：`wails generate module` 在生成前端绑定时报 `Not found: time.Time`——Wails 的类型映射器不认识标准库的 `time.Time`，导致前端拿不到该字段的类型定义。

**结论**：

- 字段类型改为 `string`，存储 RFC 3339 格式（`time.Now().Format(time.RFC3339)`）
- 排序直接比较字符串：RFC 3339 的年-月-日在前且位宽固定，字典序与时间顺序一致，无需解析回 `time.Time`
- 前端可用 `new Date(installedAt)` 直接构造 Date 对象
- 一般原则：**跨 Wails 边界的 DTO 只使用基础类型**（string / number / bool / slice / map / 自定义 struct）。引入标准库复合类型会让绑定生成静默丢字段

## 2026-07-27: 部署文件名限定为纯 ASCII

**背景**：实机联调时发现，部署 `Street Fighter™ 6_1364780.lua` 会导致 Steam 立即闪退，而同一批次的 `ARK_ Survival Ascended_2399830.lua` 正常生效。前者含全角商标符号，后者为纯 ASCII。

Debug 版 OST 的 `package.log` 定位了崩溃点：

```plain
[05:33:01.406] Processing 1 Lua file change(s)
[05:33:01.406] Lua file added: D:\Steam\config\lua\Street Fighter™ 6_1364780.lua
（日志到此中断，随即弹出 MSVC "abort() has been called"）
```

日志在打印文件名之后、`ParseFile` 结果之前中断，说明 OST 在拿到路径后、解析内容前即已终止。推断为其 `Encoding` 模块在宽字符与 UTF-8 之间转换路径时触发断言。

此前一度误判为生成脚本内容有误（缺少 `setManifestid`），修正内容后症状不变，才转而排查文件名。

**结论**：

- `sanitizeFileName` 丢弃所有码位 ≥ `0x7F` 的字符，并将连续下划线与空格折叠为单个下划线
- 选择**丢弃**而非替换为下划线：中文名游戏（如「原神」）若逐字替换会退化成一串下划线，既难以辨认又容易撞名；丢空后由 `luaFileName` 拼接 AppID 保证唯一性
- 文件名不再具备完整可读性，属可接受的代价——定位文件依靠 `_<AppID>.lua` 后缀，`Remove` 与 `readDeployedLua` 均不依赖游戏名

**教训**：症状出现在「部署之后」时，可疑范围应同时包含文件**内容**与文件**路径**，而非默认前者。

## 2026-07-27: addappid 第二参数确认无语义，DLC 独立 Depot 采用双行注册

**背景**：OST 的 README 示例写作 `addappid(id, 0, key)` 并注明「0:Depot 1:App」，而源码分析结论为该参数被完全忽略。此矛盾长期挂为待验证项。

实机比对社区清单包后确认：区分 App 与 Depot 身份靠的是**两次独立调用**，与第二参数无关。

**结论**：

- 第二参数固定填 `1`，仅为与社区脚本保持视觉一致，不承载任何语义
- 带独立 Depot 的 DLC 必须写两行——裸 `addappid(id)` 注册 App 身份，再 `addappid(id, 1, key)` 注册 Depot 密钥
- 每个 Depot 的密钥与 `setManifestid` 必须成对出现
- 主游戏自身密钥必须输出，早期版本仅取 AppID 而丢弃密钥
- README 与实现冲突时以源码及实测为准

## 2026-07-27: 卸载后的界面残留归属注入器层，仅在文案中提示

**背景**：卸载已安装本体的游戏（SF6）后，Steam 库中的 DLC 条目不会立即消失；ARK 则表现为「条目仍在但不再显示独立下载 DLC 的体积」。

如下是OST的日志：

`package.log` 显示后端清理完全成功：

```plain
UnloadFile: removed 16 depots
NotifyLicenseChanged: 0 added, 16 removed
queued 16 UI removals, skipped 0 transient removals
```

`steamui.log` 给出未生效的原因：

```plain
RunFrame: appId 1364780 is owned again, skipping removal
RunFrame: appId 1792750 is owned again, skipping removal
RunFrame: appId 1792751 is owned again, skipping removal
```

被跳过的三项恰为主游戏与两个带独立 Depot 的 DLC，均对应磁盘上已安装的内容。OST 的 `CSteamUIAppControllerRunFrame` 在消费移除队列时会检查 `IsOwned()`，跳过用户真实拥有的条目——这是防止误删正版内容的保护机制。

**结论**：

- 许可证层面的移除是彻底的，残留仅限界面显示
- 此行为属注入器层，按「不碰注入器内部逻辑」的铁律不予干预
- `RemoveDLCs` 的返回文案需相应调整，不再无条件声称「已卸载」，而是告知本体已安装时可能需要重启 Steam 才更新显示
- 同理，`InstallDLCs` 沿用「已添加到库」的表述仍然成立——安装方向的刷新经实测正常

## 2026-07-27: Steam 界面上的 DLC 日期显示不再追查

**背景**：Steam 的 DLC 管理列表显示日期为 2021-07-09，与清单包内任何时间戳均不吻合。

`steamui.log` 证实 OST 的注入行为正确：

```plain
FillInAppOverview: set PurchasedTime=1785102027 for appId=1364780
```

该时间戳换算为 2026-07-27 05:40:27，与 `.lua` 文件的 mtime 一致。

**结论**：

- `PurchasedTime` 注入链路无误，界面所显示日期取自何字段成因未明
- 不影响功能，不再投入排查
- 此项从待验证清单中移除，不作为已解释项归档——避免为未经证实的推断留下记录

## 2026-07-27: 在线仓库定为聚合社区源，不自建仓库

## 2026-07-27: 清单获取走 codeload，不申请 GitHub Token

**背景**：竞品要求用户自行申请 Personal Access Token，理由是未认证的 GitHub API 限速 60 次/小时。但其代码同时实现了一条完全不需要 token 的路径，仅作为「API 耗尽」后的兜底。

**结论**：

- 主路径使用 `https://codeload.github.com/{repo}/zip/refs/heads/{appID}`，不消耗 API 配额、无需认证

- 不引入任何 token 配置项。要求用户前往 GitHub 开发者设置申请凭据，与「解压即用」的产品定位相悖
- 镜像回退链沿用竞品验证过的顺序：`gh-proxy.org` → `cdn.gh-proxy.org` → `edgeone.gh-proxy.org` → 直连
- 不做地域主动探测。直连失败自然降级即可，省去启动期的额外请求

## 2026-07-27: 解析结果落盘为 packages/\*.json，压缩包不予保留

## 2026-07-27: manifest ID 不可比较大小，不做版本新旧判定

**背景**：设计「过期检测」时需要判断本地清单与仓库清单的新旧关系。

**结论**：

- `setManifestid` 的 manifest ID 是 Steam 内部的 64 位标识符，非递增序号。两个 ID 之间**无法判断先后**，此路不通
- manifest ID 是 per-depot 而非 per-game 的。一个游戏含本体与多个 DLC 的独立 depot，各有其 ID，因此「该游戏的版本」并不存在
- 被 `setManifestid` 钉住的构建不会自动更新。此特性既是功能（可停留于特定可用版本）也是隐患（游戏更新后仍处旧版）
- 界面不展示 manifest ID，改为展示「清单获取时间」与「来源」——前者对用户有意义，后者可追溯。原始 ID 置于详情页折叠区

## 2026-07-27: 过期检测采用按需检查，不做实时监测

**背景**：期望能实时监测已部署 Lua 是否过期。评估三条参照路径后确认可行性有限。

| 参照物           | 可行性                                                  |
| :--------------- | :------------------------------------------------------ |
| Steam 官方最新   | 不可行。未授权客户端无法获取「当前最新 manifest ID」    |
| 仓库分支更新时间 | 可行但有代价。需 GitHub API，60 次/小时的配额经不起轮询 |
| manifest ID 自身 | 不可行。见上一条决策                                    |

**结论**：

- 不做启动轮询，不做后台定时任务
- 已安装列表提供「检查更新」按钮，由用户主动触发
- 检查优先用 codeload 的 HEAD 请求读 `Last-Modified`（不耗配额），失败再退到 GitHub API
- 检查结果表述为「仓库有更新」而非「本地已过期」。前者是客观事实，后者是价值判断——旧版本时常正是用户所需（如兼容特定 MOD）

## 2026-07-27: 勾选即生效，前端 800ms 防抖聚合

**背景**：v1.4 采用「勾选后点击安装/卸载选中项」的两步式交互。OST 具备 500ms 防抖的热重载能力，该设计未加利用。

**结论**：

- 勾选状态即部署状态，取消「安装/卸载」按钮
- 勾选先只改内存状态，界面立即响应；800ms 内无新操作才落盘一次。取值大于 OST 的 500ms 防抖窗口，确保聚合完成后只触发注入器一次
- 界面以轻量状态指示同步进度，不使用阻塞式弹窗
- **取消勾选带独立 Depot 的 DLC 需二次确认**：撤销许可证后 Steam 可能判定本地内容不应存在而将其删除。此行为属 Steam 侧，无法干预，但必须使用户知情
- **全部取消勾选不等于卸载游戏**：主游戏的 `addappid` 与其密钥必须保留输出，否则已安装本体的游戏会令 Steam 崩溃（见格式契约）。彻底卸载是删除文件，为独立操作

## 2026-07-28: 检查更新采用 302 重定向探测，不实现自更新

**背景**：Release 经蓝奏云与 GitHub Release 双渠道分发。需确定版本源与检查方式。

GitHub API 的 `/releases/latest` 受 60 次/小时的未认证配额限制，而网页路由 `github.com/{repo}/releases/latest` 会 302 至具体 tag，从 `Location` 头即可读出版本号，**不消耗配额**。

**结论**：

- 版本源以 GitHub Release 为准。蓝奏云为便利渠道，但其无可供程序查询的接口，不作版本判定依据
- 检查分两级，配额仅在确有更新时消耗：

  | 阶段         | 手段                                          | 执行时机   |
  | :----------- | :-------------------------------------------- | :--------- |
  | 判断有无新版 | 不跟随重定向，读 302 的 `Location`            | 每次检查   |
  | 取更新说明   | `api.github.com/repos/{repo}/releases/latest` | 仅当有新版 |

- 国内访问失败时复用清单下载已定的 `gh-proxy` 回退链，不另建一套
- **不实现自更新**。下载可执行文件并替换运行中的自身，一旦分发链路被劫持即等同执行任意代码。仅弹出提示并打开浏览器，使下载链路对用户可见、可核对。此取向与「不负责安装/修复注入器」的铁律一致
- 提示提供 GitHub 与 B 站动态两个出口，后者含蓝奏云链接
- 支持「跳过此版本」，写入 `config.json` 的 `skippedVersion`。不提供关闭手段的提示会演变为骚扰
- 启动时检查，24 小时内最多一次，结果缓存；设置页提供手动触发；提供总开关
- 检查失败静默处理，仅记日志——此失败不属用户需要知晓的事项
- **版本号于编译期注入**：`go build -ldflags "-X main.appVersion=<版本>"`。硬编码必然导致源码与 tag 漂移，且用户报告的版本号将不可信
- **预发布版本不计为更新**：带后缀的版本仅在用户当前亦为预发布版时提示

**发布流程约定**：蓝奏云上传先行，GitHub Release 作为整条发布链的最后一步。Release 一经发布，在线客户端即开始提示新版本，若此时蓝奏云尚未就绪，用户将访问到失效链接。

## 2026-07-28: 三源并非同构——ManifestHub 停用，MAU 需专用解析器

**背景**：07-27 的「聚合社区源」决策假定三个内置源同为 GitHub 分支型、结构等价、互为备份，一套代码即可全覆盖。⑤ 施工后的实测推翻了这一假定。

以 Street Fighter 6（1364780）与 ARK: Survival Ascended（2399830）为样本：

| 源          | 实测结果                                                             |
| :---------- | :------------------------------------------------------------------- |
| ManifestHub | `git ls-remote --heads` 仅返回 `main`，所有 AppID 分支均 404         |
| MAU         | 可下载，但包内**无 `.lua`**，仅 `Key.vdf` + `config.json` + manifest |
| MAU 镜像    | 同上，且额外嵌入整个 Python 项目源码目录                             |

`processZipFromPath` 遂在解析环节直接报「压缩包中未找到 .lua 文件」，在线路径断在最后一步。

**结论**：

- **ManifestHub 默认停用**（`Enabled: false`）而非删除。仓库本体仍存在，将来恢复分支只需改回 `true`；删除则需重新考证地址与形态。启用一个必然失败的源只会让每次查找多等一轮探测
- **新增 `repo_package.go`**，从 `Key.vdf` + `config.json` + manifest 文件名直接构建 `GamePackage`，不生成中间 `.lua` 再解析——绕一圈只会多一层出错机会
- MAU 的 `config.json` 用 `packagedlcs` 字段显式标出带独立 Depot 的 DLC，比从 Lua 注释启发式推断可靠
- 解压逻辑不假定包内层级，递归遍历后按文件名与内容特征识别。两个源的目录结构本就不同
- 读 VDF 用正则而非重新引入 `andygrunwald/vdf`。⑨ 阶段刚为缩减依赖面移除了它，为读三行文本请回来不值得

**教训**：「多源互为备份」这一表述隐含了「结构等价」的前提，而该前提从未被验证。调研竞品得知源的**地址**不等于得知源的**格式**。

## 2026-07-28: 清单包格式按内容分派，不按来源假定

**背景**：三源结构互异后，需决定如何选择解析路径。按源名称硬编码是最直接的写法。

**结论**：

- 依据包内是否存在 `.lua` 分派：有则走 Lua VM，无则按 MAU 形态解析。判别只读 zip 中央目录，开销与包体积无关
- 不按源名称判断。上游随时可能调整打包脚本，届时按名称分派会**静默失效**——包能下载、能解压，只是解析结果为空或残缺，而这类故障远比直接报错难排查
- 此设计使新增源无需改动分派逻辑，只要产出形态落在已知两类之内

## 2026-07-28: MAU 的 DLC 密钥分散于各自分支，需按需补齐

**背景**：MAU 主游戏分支的 `Key.vdf` 只含主 Depot 一个密钥。SF6 的 `packagedlcs` 列出 1792750 与 1792751，但两者的密钥均不在该分支内。

实测确认 MAU 为每个带独立 Depot 的 DLC 单独开了以其 AppID 命名的分支，密钥与 manifest 在其中。

**结论**：

- 解析主包后，对缺密钥的 `packagedlcs` 各拉一次自己的分支补齐
- 并发执行但限 4 路。DLC 数量可达二十以上，全量并发会触发公益代理限流，反而更慢
- 单个 DLC 补齐失败不中断整体，该 DLC 退化为单行注册。整个游戏因一个 DLC 而完全失败是更差的结果
- 补齐的必要性不在于「少显示一个体积」：缺密钥时生成脚本退化为裸 `addappid`，Steam 无法解密该 DLC 内容，用户勾选了却装不上

**同时确认 MAU 的收录存在实质缺口**：ARK 的 `packagedlcs` 为空数组，四个 DLC 全部列入普通 `dlcs` 且均无独立分支，而其中 2827030（ARK The Center Ascended）确有独立 Depot。此为源侧数据不全，非本工具可修正。

## 2026-07-28: 自动模式下载前先做收录检测

**背景**：`Fetch` 的自动模式按顺序遍历所有启用的源，每个源再走四级镜像链。

实测 SF6：ManifestHub 未收录，四个镜像各如实返回 404，而 404 与「代理故障」在下载逻辑内无法区分，只能逐个重试至链尾。单个未收录的源白耗约 20 秒，总耗时 24.4 秒。

**结论**：

- 自动模式先执行一次 `Lookup`（三源并发，代价不足 3 秒），仅对命中的源尝试下载。实测总耗时降至 5.5 秒，尝试次数由 5 次降至 1 次
- 检测结果为空时**原样返回全部候选**而非直接判定失败。HEAD 请求可能因网络抖动或代理拦截而全部失败，此时仍应让下载链路试一遍——检测只是优化手段，不应拥有否决下载的权力
- 指定源的模式跳过检测。用户已明确选择，再检测一次只是多等一轮

## 2026-07-28: token 决策改写——用户自备的账户凭据可作可选增强

**背景**：07-27 的「不申请 GitHub Token」决策措辞为「不引入任何 token 配置项」。而 Hubcap Manifest（M 站）的数据完整度显著高于 MAU，接入它需要用户提供 API 凭据，与该措辞直接冲突。

重新审视后认为原措辞混淆了两类凭据：

| 类型                | 性质                                       |
| :------------------ | :----------------------------------------- |
| GitHub PAT          | 纯技术负担。申请它只为绕过限流，于用户无益 |
| M 站 API Key        | 用户自身的账户与额度，代表其个人权益       |

**结论**：

原则改写为：**不为绕过第三方限流而要求用户配置凭据；用户自愿提供的、代表其自身账户额度的凭据可作为可选增强。**

- 该类源的定位**与本地导入等同**：可选增强，非底层主逻辑。未配置凭据时整条链路静默跳过
- 免凭据可用是底线。不得出现「没有凭据就不能用」的状态，MAU 仍是默认路径
- **绝不内置任何共享凭据**。两条理由各自即足够：分发的 exe 内的密钥必然被提取（`strings` 一遍即得）；数千用户共用一份凭据的流量特征与爬库无法区分，而该站明令禁止爬库且处罚为永久封禁
- 未配置时**静默跳过而非报错**。用户从未打算使用该源，界面上不应出现形似故障的提示

## 2026-07-28: M 站接入采用 /manifest 端点，认证请求不经镜像

**背景**：M 站提供两个可取得清单的计费端点。需确定用哪个，以及认证请求如何处理回退。

实测 ARK（2399830）对比：

| 端点                      | 体积     | `addappid` | `setManifestid` | 额度  |
| :------------------------ | :------- | :--------- | :-------------- | :---- |
| `/api/v1/lua/{app_id}`    | 3.2 KB   | 33         | **0**           | 1 次  |
| `/api/v1/manifest/{app_id}` | 11.32 MB | 33         | **13**          | 1 次  |

同源对比 MAU：DLC 数 4 → 19，`setManifestid` 1 → 13。

**结论**：

- **使用 `/manifest`，永不使用 `/lua`**。两者同耗 1 次额度，但后者返回的脚本内 `setManifestid` 数量为零，违反部署脚本的格式契约。多传 11MB 换取数据完整性是值得的——包内 manifest 文件解析完即丢，OST 会自行下载
- 亦不使用 `/lua/basegame` 与 `/lua/dlc` 分段端点：各计一次额度，取全量数据反而消耗两次
- **绝不遍历 `/api/v1/library`**。该端点免额度且支持分页，但遍历十余万条正是该站定义的爬库行为。ARCHITECTURE 早已移除 `FetchRepoList`，此处与之一致
- 收录检测走 `/api/v1/status/{app_id}`（免额度），优于 HEAD：明确区分「未收录」与「已知但尚未生成清单」，并附带 `game_name` 与 `file_age_days`。后者使过期提示可从含糊的「仓库有更新」升级为「清单为 2 天前生成」
- **认证请求不走镜像链**。将携带凭据的请求交由第三方公益代理转发，等同于把用户凭据交给代理运营方。宁可直连失败
- 凭据只经 `Authorization` 头传递。该站文档亦支持 `api_key` 查询参数，但查询参数会进入服务端与各级代理的访问日志
- 日志中不输出凭据内容，仅记录「已设置 / 已清除」
- 清单包体积上限由 64MB 提至 512MB。ARK 的单个主 Depot manifest 即达 9.7MB，体量更大的游戏会显著更高

**附带收获**：M 站的 Lua 含完整注释与 DLC 名称，现有 `parseCommentHeader` 与 `buildDLCNameMap` 原样即可解析，游戏名与全部 DLC 名无需再查商店接口。为 MAU 形态所留的「按需查询 DLC 名称」待办在此路径上不存在。

**凭据有效期为该源的主要摩擦点**：默认仅 7 天（捐助者 90 天）。`/user/stats` 为免额度端点，可读出 `api_key_expires_at`，故在剩余不足 3 天时以顶部横幅提示。不主动提示的话，用户只会在某次下载失败时才发现，且无从判断原因。额度耗尽同理，须明确告知「今日额度已用尽，UTC 零点重置」而非笼统报失败。

**另需注意**：该站 `/search` 的结果排序不以相关度为准——搜索「Street Fighter 6」返回 19 条匹配，但前三条为原声带、Open Beta 与街霸 II 主题曲，本体不在其中。故主搜索仍用 Steam 官方 storesearch，该站的 search 仅适用于确认其库内是否存在指定条目。

## 2026-07-28: 动效以 transform 驱动，须尊重 prefers-reduced-motion

**背景**：PCL2 的活力感源自 WPF 的 `Storyboard` 与缓动函数。CSS 实现同等效果更为简洁，且 `transform` 由合成器线程处理不占主线程——此处 Wails 相较 WPF 反居优势。

**结论**：

- 缓动与时长定为设计令牌统一取用，不在组件内散落魔法数值
- `--ease-enter` 的第二个控制点取 1.4（大于 1）以产生过冲，元素略越终点再弹回。此即「弹性感」的来源
- 时长不超过 300ms；以 `transform` 与 `opacity` 驱动，避免触发布局重排
- 列表错峰入场，每项延迟 20~30ms
- **必须实现 `prefers-reduced-motion` 媒体查询**。过多动效会令前庭功能障碍用户产生眩晕，一条媒体查询的成本没有不做的理由
- 壁纸与内容之间垫半透明遮罩，透明度随主题变化。用户可能选择浅色图片致使暗色主题的文字不可读；遮罩承担主要压暗职责，模糊仅作点缀

## 2026-07-28: 反馈体系分四种形态，以「是否需要决策」划分

**背景**：需在模态弹窗与 Toast 之间取舍。若无明确规则，划分会退化为「重要的用弹窗、次要的用 Toast」这类凭手感的判断。

**结论**：

判据是**用户是否必须做出选择**，而非事情是否重要。信息再重要，只要无需决策，便不应阻断用户。

```plain
需要用户拍板？
├─ 是 → 后果难挽回？
│        ├─ 是 → 模态弹窗（遮罩 + 模糊）
│        └─ 否 → 内联确认（原地展开，不遮挡）
└─ 否 → 存在持续过程？
         ├─ 是 → 原地状态指示
         └─ 否 → Toast
```

四种形态并存。其中**原地状态指示与顶部横幅使用频次最高**，而它们既非弹窗亦非 Toast：

- 下载进度若用 Toast，用户切换页面即失去进展感知；置于游戏页则返回时仍可见
- 更新提示**不使用弹窗**。启动即以模态框遮挡界面仅为告知有新版本，属典型打扰，改用可关闭的顶部横幅

**模态弹窗的约定**：

- **默认焦点置于安全选项**，危险按钮不作主视觉强调。用户习惯性回车时应落在「不执行危险操作」
- **给出具体后果与体积**。「43.2 GB」远比「可能删除内容」有力，数字使代价可感
- **「本次会话内不再提示」限定于会话**，不写入配置。批量操作时连续弹窗是折磨，但持久化会使用户因很久之前的一次勾选而永久失去保护
- **Esc 与点击遮罩一律等于取消**，永不等于确认。误触的代价必须是「什么都没发生」
- 焦点锁定于弹窗内，关闭后归还触发元素；不嵌套弹窗，多步流程在同一弹窗内切换内容

**Toast 的约定**：

- 右下角堆叠，同时最多三条，超出挤出最旧者
- 成功类 3 秒自动消失；**警告与错误类不自动消失**——飘走的错误等同于未曾提示
- **所有警告与错误同时写入日志**。Toast 消失后无从追溯，日志是唯一留存

**性能**：`backdrop-filter: blur()` 虽由 GPU 加速，但背后铺有用户壁纸时，全窗口大面积模糊在集显设备上可能掉帧。半径控制在 8~12px，由半透明遮罩承担主要压暗效果。

## 2026-07-28: 前端以「唯一真相在 Go」为首要原则

**背景**：v2.0 的交互复杂度高于常规 SPA——跨页面共享环境状态、勾选即部署、后端推送进度，需确立前端架构。

**结论**：

- **前端不持有状态所有权**。所有 Pinia store 均为后端状态的镜像而非所有者，每个 store 须有明确的刷新时机，不自行维护推导出的状态。违反此原则会立即产生漂移——界面显示已装 3 个 DLC，实际部署文件中却是 5 个
- 因此本项目的数据流较一般 SPA **更为简单**：后端说什么即是什么，前端无需操心一致性。真正的复杂度在交互打磨，不在数据流
- **组件不得直接 import wailsjs**，一律经 `api/` 层。该层吸收生成代码的形态差异，Wails 升级改变生成规则时只需改动一处
- **路由使用 `createWebHashHistory`**。Wails 经自定义协议提供页面，history 模式在部分情形下刷新会 404
- `/game/:appID` 单一路由承担未入库与已入库两种状态。不拆为两个路由——否则入库成功后需路由跳转，过渡动画与返回逻辑均会复杂化
- Store 按「谁需要读它」划分而非按数据类型。搜索结果与 DLC 勾选状态**不进 store**：前者为会话级临时数据，后者归属「当前所看的这一个游戏」，置于全局反而需处理切换时的清理
- **确认弹窗以 Promise 呈现**而非回调或事件总线，使决策逻辑得以线性书写而不被割裂为两处
- 下载进度经 Wails 事件推送，**组件卸载时必须 `EventsOff`**。否则切页面再返回会重复注册，同一事件收到多份，是 Wails 项目中常见的隐性缺陷
- `OperationResult` 由 `api/` 层归一化为异常语义，避免每个组件同时书写 `Success` 判断与 `try/catch` 两套分支

## 2026-07-28: OST 按并集去重加载全部 Lua，不存在文件级优先权

**背景**：先前假定「同一 AppID 被多个 Lua 文件声明时会互相覆盖」，并据此设想通过命名前缀为盒子的产物争取加载优先级。该假定未经验证，而它直接决定卸载逻辑与外部文件的处理方式，故以 ARK（2399830）为样本做实机验证。

验证方法为在 `config/lua/` 同时放置两个均声明主游戏 2399830、但 DLC 完全不重叠的文件：一个模拟用户手动放置（纯数字命名，1 个 DLC），一个模拟盒子产物（含 3 个 DLC）。

**结论**：

- **加载方式是并集去重，而非文件覆盖**。日志中 `InitFakeLicense(PackageId=0): adding 8 apps` 精确等于两文件 AppID 去重后的数量（而非 3+7=10），Steam 界面亦如实呈现两文件 DLC 之和
- 成因在于 `LuaConfig` 的 `DepotKeySet` / `ManifestOverrides` 等均为**全局 map**，`ParseDirectory` 遍历全部 `.lua` 并将结果合并写入同一批容器。文件不构成独立作用域
- **因此不存在文件级的优先权**。同一 key 被多份文件写入时，胜出者仅取决于谁后 Parse，而 Parse 顺序在启动时由目录遍历序决定、在运行时由 watcher 事件序决定，**两者盒子均无法控制**
- **推论：靠命名前缀抢占优先级的思路无效，不必实现**。此方向已排除，避免后续重复设想
- 该结论的另一面是外部文件不会被盒子的部署压制。用户手动放置的清单与盒子的产物共存时，两者的 DLC 会同时出现在 Steam 库中

## 2026-07-28: 引用计数使卸载可能部分失效，卸载前须扫描其他文件的声明

**背景**：承上一条实验，删除其中一个 Lua 文件后观察许可证层的实际变化。源码分析中提到 `LuaConfig` 持有文件级引用计数 `g_depotRefCount`，「UnloadFile 时减计数，计数归零才真正移除 depot」，此机制的实际后果先前未被评估。

**结论**：

- **共享 AppID 的许可证不会随单个文件的删除而移除**。实测删除盒子产物后，日志显示：

  ```plain
  UnloadFile:Ref count for AppId 2399830 is 2   ← 另一文件仍持有
  UnloadFile: removed 7 depots from ...lua      ← 文件账本注销 7 个
  NotifyLicenseChanged: 0 added, 5 removed      ← 许可证层仅移除 5 个
  ```

  `7` 与 `5` 的差额即为两个被共同声明的 AppID（主游戏 2399830 与主 Depot 2399831），其 refCount 由 2 减为 1 而未归零，故许可证保留。随后 `FillInAppOverview: set PurchasedTime for appId=2399830` 确认 Steam 依然认为用户拥有该游戏

- **危害在于卸载功能会对用户撒谎**。盒子删除自己的文件、清除历史记录、提示「已卸载」，而游戏仍在 Steam 库中且重启亦不消失（因另一文件仍在磁盘上）。此时盒子已遗忘该游戏，用户连重试卸载都无从下手
- **故卸载前必须扫描部署目录中其他 Lua 文件是否声明同一 mainAppID**。若有，不得报「已卸载」，而应如实告知「检测到其他清单文件同样声明了本游戏，游戏可能仍保留在 Steam 库中」并指出具体文件名
- 此约束同时适用于「已识别的用户体验缺口」中的外部文件对账功能——两者所需的能力是同一个：按内容而非文件名确定哪些文件声明了某个 AppID

## 2026-07-28: 删除文件不触发存活文件重新解析，冲突的密钥值残留至重启

**背景**：既已确认多文件写入同一 map key，则需查明「删除后写的那份文件后，先写的声明是否会被恢复」。实验方法为令两文件声明同一主游戏但密钥不同（一份为真密钥，一份替换为等长的可辨假值 `123456789...`），观察删除其一后的行为。

**结论**：

- **`UnloadFile` 不会重新解析存活的文件**。日志明确显示 `NotifyLicenseChanged: processing 0 additions`——OST 仅执行「减计数、归零则移除」，不回头重读仍在磁盘上的其他文件
- **后果是内存中残留一个已不存在于任何文件的密钥值**。若用户先有外部文件（错误密钥）、后被盒子部署（正确密钥）覆盖该 key，再卸载盒子的部署，则 `DepotKeySet` 中留存的仍是盒子那份**已被删除的**密钥。磁盘上只剩错误的那份，而内存与磁盘不一致
- **该不一致仅在重启 Steam 后收敛**。即同一套磁盘状态，重启前与重启后行为不同——排查此类问题时若不重启，观察到的现象无法复现
- **密钥冲突完全不可观测**。OST 对同 key 覆盖不输出任何警告（无 `Duplicate` / `overwrite` 类日志，亦无 warn 级别记录），且从不将密钥值写入日志（此举本身正确，密钥属敏感数据）。故无论从日志或界面均无从判断当前生效的是哪一份密钥
- **推论：盒子是唯一有机会在事前发现冲突的环节**。一旦部署落盘，冲突即不可见，症状将表现为「一切正常，直到下载时解密失败」，而线索链完全断裂。此即在部署前主动扫描并告知的根本理由，而非仅为界面友好
- 未验证的部分：究竟哪一份密钥最终胜出。因密钥仅在解密 depot 内容时才被实际使用，验证需真实下载游戏本体（样本体积 227 GB），代价过高。**且此答案不改变设计——无论谁胜出，应对方式均为告知用户冲突**，故不再追查

## 2026-07-28: SteamTools 与 OST 共用劫持入口，卸载顺序必须写入教程

**背景**：为保证上述实验不受第三方注入器干扰，需先清空 SteamTools 环境。执行社区流传的卸载步骤时发现其中隐含陷阱，而该陷阱对本项目的用户群体具有普遍性——v2.0 的目标用户几乎全部是 ST 时代的迁移者。

社区卸载步骤要求删除 Steam 根目录下的 `hid.dll`、`XInput1_4.dll`、`dwmapi.dll` 三个文件。

**结论**：

- **`dwmapi.dll` 与 `xinput1_4.dll` 是 ST 与 OST 共用的文件名**。二者均采用同一套 DLL 劫持手法，靠这两个代理入口被 Steam 加载后再转载各自的核心 DLL。ST 独有的仅 `hid.dll` 与 `config/stplug-in/`
- **因此照社区步骤操作会连带删除 OST 的劫持入口**，仅留下孤立的 `OpenSteamTool.dll`。表现为 OST 完全不加载、不产生任何日志、盒子的环境检测判定为未就绪，而用户以为自己只是卸载了旧工具
- **教程必须明确「先卸载 ST，后安装 OST」的顺序**，并说明若已安装 OST 再执行 ST 卸载步骤，需重新补齐这两个代理 DLL
- **「不要同时使用其他入库软件」应作为前置要求置于教程开头**，而非列为注意事项。理由是 ST 残留并非静态垃圾，而是**第二个正在运行的注入器**：其痕迹写在 Steam 自身（`config.vdf` 的 depot 密钥、`depotcache/` 的 manifest、`config/stplug-in/` 的脚本），与 OST 处于同一层级，同一 AppID 会被两套机制各自注入
- 教程需给出的清理清单：`hid.dll`、`config/stplug-in/`、`config/depotcache/`、`appcache/httpcache/`，以及经 ST 自带卸载程序执行的卸载
- **盒子可检测 ST 残留并挂横幅告知，但不得代劳清理**。检测属于状态提示，符合既定的职责边界；代为删除文件则越过「不帮安装不帮修复注入器」的界限

## 2026-07-29: 开发模式判据由环境变量改为构建标签

**背景**：施工「数据目录改为 exe 同级」时依原决策实现 `KAZEUSA_DEV=1`，却发现 **Wails v2.11 的 `wails.json` 并无注入环境变量的字段**（已核对 `internal/project/project.go`）。原决策中「固化于 wails.json 的 dev 配置，无需每次手动设置」这一前提不成立。

排查中发现 Wails 自身以构建标签区分运行模式：`internal/app/app_dev.go` 为 `//go:build dev`，而 `wails dev` 必然携带该标签。

**结论**：

- **改用 Go 构建标签 `dev` 判别开发模式**。新增 `buildmode_dev.go`（`//go:build dev`）与 `buildmode_prod.go`（`//go:build !dev`）两个互斥文件，各定义 `isDevBuild` 常量
- 此法优于环境变量：**判据由构建方式决定，无从遗漏或误设**。环境变量需人工配置，一旦忘记便会把数据写入构建输出目录，随下次清理一并消失，且该失效是静默的
- 同时**取消 `KAZEUSA_DATA` 这一层**。原决策将其列为最高优先级，但它服务于「用户自定义数据位置」这一尚无人提出的需求，且引入了「配置存放位置本身需要配置」的循环。待确有需求再加
- 修正后的选址顺序：

  | 优先级 | 条件           | 目录                |
  | :----- | :------------- | :------------------ |
  | 1      | 开发构建       | `~/.kazeusa`        |
  | 2      | 默认           | exe 同级 `.kazeusa` |
  | 3      | exe 目录不可写 | 回退 `~/.kazeusa`   |

- 「不以路径特征推断运行环境」这一原则维持不变，且构建标签比环境变量更贴合该原则
- 可写性判定不止于 `MkdirAll` 成功：目录可能已存在却拒绝写入文件（Program Files 下的 UAC 虚拟化即如此），故额外做一次探针文件写入并立即删除

**教训**：决策中凡涉及「某工具支持某配置项」的前提，落档前应实际查证。本条的返工源于假定 Wails 具备一个它并不具备的能力。

## 2026-07-29: 清单文件定位改按内容匹配，并建立测试基线

**背景**：⑤ 完工后复查发现 `readDeployedLua` 以 `_<AppID>.lua` 后缀扫描目录定位文件，只能识别本工具自己生成的命名。而 07-28 的实测已确认注入器加载目录内全部 `.lua` 的并集，外部文件同样在生效。

该缺陷的表现是静默的：用户手动放置的 `2399830.lua` 匹配失败后，`detectInstalledDLCs` 走入「未部署过此游戏」分支，界面显示全部 DLC 未安装，而 Steam 中实际已装。

**结论**：

- **定位一律按内容匹配 `addappid(<appID>`，不得依赖文件名**。外部文件可为任意命名，靠命名约定识别必然漏判
- 新增 `findLuaFilesDeclaring`（返回声明某 AppID 的全部文件）与 `externalDeclarations`（滤出其中非本工具产物者）。**部署与卸载前均调用**：卸载时若存在外部声明则不报「已移除」而返回失败并列出文件名；部署时以警示文案提示密钥可能冲突
- 新增 `ScanDeployed` 与 `DeployedEntry`，供界面按磁盘真实状态渲染而非依赖本工具的记忆
- `Deployer.Remove` **维持只删自己命名格式的文件**。外部清单属来源不明的第三方文件，代为删除属越权，且其中可能含用户特意配置的内容。此取舍的代价（卸载可能不彻底）由上述冲突提示承担

**顺带修正一处正则缺陷**：`[^-]` 在 Go 的正则中**会匹配换行符**，故 `[^-]*addappid\(` 中的贪婪量词会跨行吞噬整段文本，使 `FindAllStringSubmatch` 只返回最后一处匹配——表现为「文件声明了 20 个 AppID 却只识别出 1 个」。已改为 `[^-\n]*?`。

原有的 `luaContainsAppID` 存在同一隐患，只因它仅判断有无匹配、跨行吞噬不影响布尔结果而未暴露，一并修正。**此类缺陷靠肉眼审查难以发现，是本项目引入测试的直接动因。**

**建立测试基线**：新增 `lua_match_test.go` 与 `app_scan_test.go`，共 18 个用例，为项目首批测试。选择这两处起步是因其为纯逻辑、无副作用，且失效方式均为静默返回错误结果而非报错——正是最需要测试锁定的一类代码。上述正则缺陷即由测试捕获。
